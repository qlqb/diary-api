# 교재 목차 하위항목 보존 — 계획 v2 (2026-10-06)

브랜치 `feat/toc-subitems`(diary-api `wt/api-toc`, diary-ui `wt/ui-toc`), 기준 dev-playground(api `8268554`, ui `a314d84`).
v1 → v2: Codex 계획 리뷰 14건 반영(§11 표). 핵심은 **단계 분리** — 이번에는 "읽기 복구 + 원문 열쇠 + 같은 원문 안의 확실한 대응에서만 하위항목 ADD",

## 0. 문제

웹 목차(서점 페이지) 원문 142줄 중 14줄(Chapter 줄)만 목차로 읽힌다(로컬 `memo` 리비전 15, 리비전 11·14도 같은 모양).

| 원인 | 위치 |
|---|---|
| 쪽 번호 없는 `01 제목` 줄을 버린다(본문 번호 목록 대비 규칙인데 웹 목차는 목차 블록만 잘라 온 것) | `TextbookExtractor.parseLine` |
| `실습 1-1 …`·`요약`·`연습문제`·`요약/연습문제`·`부록 A. …` 규칙이 없다 | 같은 곳 |
| `Chapter 01`과 `01 …`이 같은 깊이 | 같은 곳 |
| 모델 보조는 규칙이 하나도 못 읽었을 때만, 깊이 0~2만, 160줄까지 | `TextbookLookupWorker` 434행, `fromModelPicks`, `TextbookModelAssist.MAX_TOC_LINES` |
| 저장 때 깊이 0~3으로 자르고 골격은 3단계 아래를 버린다 | `WebTocStructurer.sanitize`, `TocSkeleton.MAX_DEPTH` |
| 캐시가 페이지 파서 판만 본다 — 같은 원문을 새 규칙으로 다시 구조화하지 않는다(페이지 캐시·ISBN 캐시 둘 다) | `WebEvidenceStore.cached`·`byIsbn` |
| `tocLine`이 "구조화 목록의 몇 번째"다. 규칙이 바뀌면 같은 번호가 다른 항목을 가리킨다 | `TocOps.checkAdd`, `TocSkeleton`, `TopicTreeEditor`, 저장된 정리안 `ops_json` |

실제 목차 모양: `Chapter NN 제목` / `NN 절 제목`(쪽 없음) / `실습 N-M …` / `요약` / `연습문제`(또는 `요약/연습문제` 한 줄) / 끝에 `부록 A. …`.
들여쓰기가 없고, `실습 1-1`은 장 번호를 달므로 **장의 자식(절의 형제)**으로 둔다: `Chapter 01 → {01, 02, …, 실습 1-1, 요약, 연습문제}`. 원문 순서 유지.

**이미 확인한 결과(규칙 구현 후, 실제 원문을 로컬에서만 읽음 — 저장소에 넣지 않음)**: 리비전 15 142/142줄, 리비전 11 70/70줄, 못 읽은 줄 0.

## 1. 범위와 원칙

이번(1단계):
- 웹 목차 규칙·모델 보완·깊이·재구조화(모든 리비전 진입점).
- 목차 항목 열쇠(원문 해시 + 줄)로 `tocLine`의 뜻을 하나로. 열쇠 판(`toc_key_version`)으로 옛 정리안을 구분.
- 정리(tidy)에서 **같은 원문(해시 같음)으로 확실히 대응된 기존 목차 토픽 아래의 빠진 하위항목**과, 트리 전체가 목차 토픽뿐일 때의 빠진 장을 서버가 ADD로 낸다.
- 목차 제목만 있는 실습·연습문제로 문제 내용을 지어내지 못하게 서버에서 막는다.

다음 단계(이번 아님, §10):
- 자료에서 만든 토픽·사용자 토픽과 목차 항목의 대응(모델 `sameAs`), 원문이 바뀐 뒤의 열쇠 재연결(`TOC_ANCHOR`).
- 그때까지 이 경우는 **지금 동작(모델이 `tocLine` ADD를 내고 서버가 확인)**을 유지하되, 서버가 이미 대응된 항목·같은 부모의 같은 제목 형제를 가진 ADD를 버린다(§5.4).

원칙:
- 이번 작업이 내는 목차 변경은 ADD뿐이다. 기존 토픽의 ID·제목·부모·순서·자료 연결·진도·막힘 기억을 바꾸지 않는다(같은 정리안 안의 모델 RENAME·MOVE 등은 지금처럼 사용자가 고르는 별도 변경 — 이번 작업이 늘리지 않는다).
- 열쇠는 **만들 때 한 번 정하고 바꾸지 않는다**(불변). 재연결은 다음 단계.
- 조용히 버리지 않는다: 못 읽은 줄 수·상한 제외 수·대응 못 한 토픽 수를 저장하고 화면 문구까지 전달한다.

## 2. 목차 항목 열쇠

### 2.1 정의
- `TocSnapshot`에 `keyKind`(WEB·MATERIAL)·`keyHash`를 둔다. 항목은 `keyOf(entry)`·`entryByKey(key)`로만 찾는다(`entries.get(n-1)` 제거).
  - WEB: `keyHash` = 리비전 `toc_raw_hash`(목차 원문 SHA-256), 열쇠 = **원문 줄 번호**(`TocEntry.unit`, `WebTocStructurer.lines` 기준).
  - MATERIAL: `keyHash` = 자료 `file_hash`, 열쇠 = 추출 결과 순번(1부터) — 업로드 추출 규칙은 이번에 바꾸지 않으므로 지금의 `tocLine`과 같은 값이다.
- `TOC_KEY_VERSION = 2`. 정리안의 `tocLine` = 항목 열쇠. 쓰는 곳 전부: `TocSkeleton`, `TocOps.checkAdd`, `ProjectTidyAnalyzer`(프롬프트 `#열쇠`), 새 `TocReconciler`, `TopicTreeEditor.insertTree`.

### 2.2 옛 정리안·작업(Codex #2)
- `project_tidy_proposals.toc_key_version`·`project_tidy_jobs.toc_key_version` 추가(NULL = 옛 뜻 = 구조화 순번).
- 새 정리안·작업은 2를 기록. 적용·화면에서 `toc_key_version`이 2가 아니고 목차 작업(`isFromToc`)이 있으면 **목차 근거가 바뀐 것과 같이** 다룬다: 적용은 `TEXTBOOK_TOC_CHANGED`(409), 화면은 `tocStale` — 사용자가 다시 정리하면 새 판으로 만든다.
  MATERIAL 목차의 옛 정리안도 순번 뜻은 같지만 단순하게 같은 규칙을 적용한다(옛 정리안은 다시 만들기).
- 대기 중인 옛 작업(QUEUED·RUNNING)은 새 서버가 처리할 때 `toc_key_version` NULL이면 지금 판으로 실행한다(작업은 실행 시점에 목차를 다시 읽으므로 옛 번호를 들고 있지 않다). 사용자 편집 승계(`carriedUserOps`)는 사용자 작업만 옮기며 목차 작업은 승계 대상이 아님을 테스트로 확인한다.
- 배포: 로컬 단일 서버. 구·신 서버 동시 동작은 없다(문서에 명시).

### 2.3 토픽 저장
- `course_topics`: `toc_key_kind VARCHAR(10)`, `toc_key_hash CHAR(64)`, `toc_key_line INT`, `toc_key_state VARCHAR(16)` 추가.
  - 목차에서 만든 새 토픽: 세 칸을 채우고 state `SET`. **이후 바꾸지 않는다.**
  - `source_toc_seq`는 표시용 순번("목차 N번째")으로 남긴다. 짝 찾기에 쓰지 않는다.
- `textbook_web_revisions`: `toc_version INT NOT NULL DEFAULT 1`, `toc_raw_hash CHAR(64) NULL`, `toc_raw_truncated TINYINT(1) NULL`(§7) 추가.

### 2.4 기존 토픽 변환(마이그레이션, Codex #11)
대상: `source_toc_seq IS NOT NULL`인 토픽.
- 웹(`source_web_revision_id` 있음): 그 리비전이 있고 `JSON_VALID(toc_json)`이고 `source_toc_seq BETWEEN 1 AND JSON_LENGTH(toc_json,'$.entries')`이고
  `entries[seq-1].unit`이 1 이상 정수일 때만 → kind WEB, hash = 그 리비전 `toc_raw_hash`, line = unit, state `SET`. 셋을 한 UPDATE에서 함께 채운다.
  조건이 하나라도 안 맞으면 state `MISSING_SOURCE`(키 칸 NULL).
- 업로드(웹 리비전 없음): 만들 때의 파일 해시·추출 판을 확정할 근거가 없다 → 추측하지 않고 state `MISSING_SOURCE`.
- 열쇠 없는 일반 토픽(자료·사용자): state NULL(목차 토픽이 아님). `MISSING_SOURCE`와 구분한다.
- 재실행 무변화(`toc_key_state IS NULL AND source_toc_seq IS NOT NULL`만 대상). 전후 건수(SET·MISSING_SOURCE)를 SELECT로 보고.
- 로컬 `memo` 대상: 영어회화(940) 12개(리비전 8). 백업 뒤 적용.
- `toc_raw_hash` 채우기: `SHA2(toc_raw, 256)` — Java(`toc_raw` UTF-8 SHA-256)와 같은지 DB 테스트로 확인.

## 3. 웹 목차 구조화 규칙(`WebTocStructurer`, `TOC_VERSION = 2`) — 구현함

웹 목차 블록 전용 분류기(업로드용 `TextbookExtractor.parseLine`은 그대로).

| 분류 | 예 | 깊이(0부터) |
|---|---|---|
| PART | `제1부 …`, `Part 1 …` | 0 |
| CHAPTER | `Chapter 01 …`, `제3장 …`, `3장 …`, `Unit 2 …`, `Lesson 4 …` | 1 |
| SECTION_HEAD | `Section 3 …` | 장이 있으면 2, 없으면 1 |
| NUMBERED | `01 …`(쪽 없어도), `1.2 …` | 장이 있으면 1 + 상대 깊이, 없으면 상대 깊이 |
| LABELED | `실습 1-1 …`, `Lab 2 …`, `요약`, `정리`, `연습문제`, `요약/연습문제`, `확인 문제`, `Exercises`, `Summary`, `Quiz` … | 지금 장(장이 없으면 가장 얕은 번호 항목, 그것도 없으면 부)의 자식 |
| APPENDIX | `부록 A. …`, `Appendix B …` | 1(장과 같은 깊이) |
| 머리 | `목차`, `Contents` | 건너뜀 |
| 미분류 | 그 밖 | 모델 보완 후보 |

- 상대 깊이(Codex #9): **장 구간마다** NUMBERED 번호 깊이의 최솟값을 1로 본다(장 하나는 `01`, 다른 장은 `1.1`을 써도 각각 절). PART·CHAPTER·APPENDIX를 만나면 구간과 "지금 장"을 새로 시작한다.
- 이름표 단어 뒤에 글자가 이어지면 이름표가 아니다(`정리하기` ✗). `Appendix Basics`의 `B`는 부록 기호가 아니다.
- 원래 깊이를 그대로 저장한다(자르지 않음, Codex #8). 규칙이 낼 수 있는 최대 깊이는 5(부·장·`1.1.1.1`).
- 구조화 상한 `MAX_ENTRIES = 400`: 넘는 줄은 읽지 않고 `unread`에 더해 PARTIAL로 남긴다(목차에 없으므로 "목차에는 남음"이라고 하지 않는다).
- `Structured`에 `unread`(미분류 + 상한 초과 줄 수)를 둔다. `toc_json`에 `unread`·`tocVersion`을 저장한다.

## 4. 모델 보완 — 못 읽은 줄이 있으면(비율 무관)

- 조건: `unread > 0`, 모델 설정됨, 하루 호출 한도 안, 작업 기한 5초 이상.
- 입력: 원문 줄 전부(최대 400줄, `TextbookModelAssist.MAX_TOC_LINES` 160 → 400), 규칙이 읽은 줄은 `[읽음 깊이 N]` 표시. 지시: 표시 없는 줄 중 목차 항목만 `{"picks":[{"line":12,"level":2}]}`로.
  원문은 데이터 블록, 줄마다 번호. 응답은 picks만 받는다(그 밖의 키 무시).
- 합치기(서버, Codex #9 — 충족 불가능한 경우 없음):
  - 규칙 줄·범위 밖·중복·역순·머리 줄·깊이 범위(0~8) 밖 pick은 버린다. 제목·번호·쪽은 서버가 원문 줄에서 자른다.
  - 원문 줄 순서로 합친다. **규칙 항목의 부모를 먼저 확정**해 두고, 모델 항목 M의 깊이 = `clamp(pick, 아래쪽, 위쪽)`:
    아래쪽 = M 뒤 첫 규칙 항목 깊이(그보다 얕으면 그 규칙 항목의 부모를 빼앗는다), 위쪽 = `max(앞 항목 깊이 + 1, 아래쪽)`.
    뒤 규칙 항목이 없으면 아래쪽 0. 연속 모델 항목에도 같은 규칙.
  - 테스트로 "합친 뒤 모든 규칙 항목의 부모(원문 줄)가 합치기 전과 같다"를 확인.
  - method `RULE_MODEL`(규칙 0개면 `MODEL_PICK`). coverage는 규칙으로 읽은 범위 그대로(모델 결과로 PAGE_FULL이 되지 않음). 실패·시간 초과면 규칙 결과.

## 5. 정리(tidy)에서 목차와 기존 트리 — `TocReconciler`(서버, 결정적)

### 5.1 토픽 상태(Codex #3)
WEB 목차가 있을 때, ACTIVE 토픽마다:
- `MATCHED`: `toc_key_state = SET`, `toc_key_hash == 지금 keyHash`, 그 줄의 항목이 지금 목차에 있음. 한 항목에 둘 이상이면 둘 다 `AMBIGUOUS`.
- `AMBIGUOUS`: 열쇠가 있지만 해시가 다르거나(원문이 바뀜) 그 줄 항목이 없거나 중복.
- `MISSING_SOURCE`: 목차에서 왔지만 열쇠를 확정 못 함(마이그레이션).
- `PLAIN`: 목차 토픽이 아님(자료·사용자).

### 5.2 항목 상태
- `MATCHED`(대응된 토픽 있음) / `NEW`(확실히 새 항목) / `UNSURE`(판단 보류). **`NEW`만 ADD한다.**
- `NEW` 조건: 대응 토픽이 없고, 다음 중 하나
  (a) 목차상 부모 항목이 `MATCHED`이고 그 토픽 아래 ACTIVE 자식 중 정규화 제목이 같은 것이 없음, 또는 부모 항목이 `NEW`(체인),
  (b) 최상위 항목인데 트리의 ACTIVE 토픽이 모두 `MATCHED`(=트리 전체가 이 원문의 목차 토픽)이고 최상위에 같은 정규화 제목이 없음.
- 그 밖(부모가 `UNSURE`, 트리에 `AMBIGUOUS`·`MISSING_SOURCE`·`PLAIN` 토픽이 섞인 최상위 등)은 `UNSURE` — ADD 안 함, 자식도 `UNSURE`.

### 5.3 ADD
- 부모는 목차 구조로: 부모 항목이 `MATCHED`면 `parentTopicId` = 그 토픽, `NEW`면 그 ADD의 자식. 형제 순서는 원문 순서, 기존 형제 뒤에 붙인다(`afterTopicId` 쓰지 않음 — 지금 동작, Codex #10).
- `by = TOC`, `tocLine = 열쇠`, 제목·쪽은 목차 값. 최상위 `NEW` 하나(또는 `MATCHED` 부모 아래 `NEW` 묶음의 맨 위 항목 하나)가 변경 하나.
- 깊이 상한(§6)에 걸린 항목은 내지 않고 수를 센다.

### 5.4 모델과의 관계
- 트리가 비어 있음: 지금처럼 `TocSkeleton`(같은 열쇠·깊이 규칙).
- 서버 ADD가 있으면 골격처럼 프롬프트에 "[서버가 낸 목차 추가안] (이미 제안됨)"으로 보이고, 모델이 같은 항목을 또 내지 않게 한다.
- 트리에 `PLAIN` 토픽이 있으면 지금처럼 모델이 `tocLine` ADD를 낼 수 있다(자료 기반 트리의 1단계 처리). 서버는 모델 ADD 중
  `MATCHED`·`UNSURE`·서버 ADD에 이미 있는 열쇠, 그리고 목표 부모 아래 같은 정규화 제목의 ACTIVE 형제가 있는 것을 버린다.
- **트리에 `AMBIGUOUS`·`MISSING_SOURCE` 토픽이 하나라도 있으면 모델의 목차 ADD를 모두 버린다**(재리뷰 P1-1) — 그 토픽이 어느 항목인지 모르므로
  어떤 항목을 더해도 중복일 수 있다. 서버 ADD는 §5.2대로(그 토픽과 무관한 `MATCHED` 부모 아래만). 요약에 "대응을 확정하지 못한 토픽이 있어 목차 추가를 보류했어요"를 붙인다.
- §5.2 `NEW` 조건에 "그 항목에 대응을 주장하는 `AMBIGUOUS` 토픽이 없음"을 명시한다(같은 해시인데 한 줄에 둘 → 그 항목·하위 `UNSURE`).
  모델 프롬프트의 목차 줄에는 `MATCHED` 항목에 `= #토픽ID`를 붙여 이미 있는 항목임을 보인다. 목차 줄 상한 150 → 400.
- 정리안 요약 문구에 수를 붙인다: "목차 하위항목 N개 추가 제안 · 대응을 확정하지 못한 목차 항목 M개는 그대로 두었어요(다음 정리에서 다시 볼게요)".

### 5.5 변경 식별(Codex #5)
- `TopicChangePlan.signature()`: `tocLine`이 있는 ADD는 `ADD|toc|<열쇠>`(제목·부모 대신) — 장마다 반복되는 `요약`·`연습문제`가 서로의 제외·제목 편집을 승계하지 않는다.
  같은 정리안 판 사이의 승계는 목차 근거(`toc_basis_json`)가 같을 때만 일어나므로(다르면 정리안이 낡음) 해시는 signature에 넣지 않아도 된다.
- `contentKey()`(재리뷰 P1-2): 지금 내용 비교(부모·제목·자식 구성·근거)를 그대로 두고 `|toc|<열쇠>`를 덧붙인다 — 같은 열쇠라도 부모·자식이 달라지면 편집 승계에 재확인이 필요하다. 회귀 테스트: 같은 열쇠 ADD에 자식이 늘거나 부모가 바뀌면 `needsConfirm`.
- `TOC_ANCHOR` 작업은 이번에 만들지 않는다(재연결 없음, Codex #1·#5 해당 없음).

## 6. 깊이·개수 상한(Codex #8)
- 저장: 원래 깊이 그대로(§3). 모델 pick 깊이 입력 범위만 0~8.
- 학습 구조 제안(골격·§5 ADD): 트리 깊이(최상위 0부터) **8단계(0~7)**까지. 넘는 항목과 그 아래는 내지 않고 `excludedByDepth`로 센다.
- 제안 개수 상한 `MAX_NODES = 400`(구조화 상한과 같음). 넘으면 `excludedByCount`.
- 두 수는 골격·정리안 이유 문구와 정리안 요약에 나온다: "N개 항목은 너무 깊거나 많아 학습 구조에 넣지 않았어요(교재 목차 화면에는 보여요)".
- 화면: 학습 지도 트리는 재귀·기본 접힘(깊이 제한 없음). 정리안 미리보기도 재귀. 깊은 트리 들여쓰기 확인만.

## 7. 다시 구조화와 캐시(Codex #6·#7)
- 공통 `WebTocRefresher.ensureCurrent(revision, userId, budget)`: `toc_version < TOC_VERSION`이고 `toc_raw`가 있으면 저장된 원문으로 §3·§4를 돌려
  새 리비전을 저장(같은 page, `fetched_at` 유지, 내용 해시에 `tocVersion` 포함). 원문이 없으면 그대로.
- 호출 지점: worker의 페이지 캐시(`cached`) 경로, ISBN 캐시(`byIsbn`) 경로, 링크 페이지 경로 — 리비전이 결과 표에 들어가는 모든 곳.
- 잘림 여부: 새로 받는 페이지는 `toc_raw_truncated`에 파서의 잘림(서점 페이지 잘림 + `cutRaw` 20,000자 잘림 — 지금은 `cutRaw` 잘림이 표시되지 않으므로 `Parsed.tocTruncated`에 합친다)을 저장.
  옛 리비전(NULL)은 `toc_raw` 길이가 `cutRaw` 상한에 닿았으면 잘림, 아니면 잘리지 않음으로 본다(옛 coverage PARTIAL을 잘림으로 보지 않는다 — `asParsed`가 지금 그렇게 한다).
- `TocResolver.webSnapshot`: 리비전이 옛 `toc_version`이면 같은 page·같은 `toc_raw_hash`의 최신 `toc_version` 리비전(같은 사용자 범위 조회 — SHARED 또는 그 사용자)을 따라간다. 없으면 옛 것.
- `TextbookLookupService.ensure`: 조회가 살아 있고 근거가 같아도, **따라간 뒤의 유효 리비전**(고른 판·대표 리비전·교재 칸 리비전)이 옛 판이면 재사용하지 않고 새 조회를 큐에 넣는다. 유효 리비전이 현재 판이면 그대로(반복 등록 없음).
- 새 조회가 FOUND로 끝나면 지금처럼 자동 정리(근거 리비전이 바뀌었으므로 새 정리안).
- 완료 판단은 새 리비전의 항목 수·`unread`·커버리지·대응 결과로 한다(§9 실데이터).

## 8. 목차 제목만 있는 실습·연습문제(Codex #12)
- `TocItemKind.of(title)`: EXERCISE(연습문제·확인/도전/종합/실전 문제·Exercises·Quiz·Problems) / LAB(실습·Lab) / SUMMARY(요약·정리·Summary) / null.
- 서버 강제(`PlanResultNormalizer`): 계획 항목이 인용한 목차 토픽 중 EXERCISE·LAB 토픽이 있고, **그 토픽에 연결된 자료 본문 구간이 이번 호출에 전달돼 그 항목이 인용했다고 서버가 확인하지 못하면**(재리뷰 P1-3 — 다른 장의 본문을 하나 인용한 것으로는 풀리지 않는다; 확인은 전달한 구간의 토픽 연결로 한다),
  모델이 쓴 제목·설명·완료 기준을 쓰지 않고 서버 문구로 바꾼다:
  제목 `「부모 › 토픽」 풀기`(LAB은 `해 보기`), 설명 `교재 「부모 › 토픽」(교재 p.N)의 문제를 교재에서 직접 풀어요. 문제 내용은 교재에서 확인해요.`,
  완료 기준 `교재 「부모 › 토픽」 문제를 모두 풀고 답을 확인한다`(source DEFAULT), origin null(원문 과제로 표시하지 않음).
- 계획 입력에서 목차 토픽에 부모 경로와 "(목차 제목만 — 본문 없음)"을 붙인다(이번 호출에 그 토픽의 본문 구간이 없을 때).
- 테스트: 목차 토픽만 인용하고 "1번 문제: TCP 3-way handshake를 설명하라"를 쓴 악성 모델 출력 → 저장되는 제목·설명·완료 기준에 그 문장이 없다.
  목차 연습문제 토픽 + **무관한 다른 장 본문**을 함께 인용 → 서버 문구로 바뀜. 그 연습문제 토픽에 연결된 본문 구간을 인용 → 모델 문구 유지.

## 9. 보안(Codex #13)
