## 1. 착수 전에 코드로 확인한 것

지시 문서가 "확인을 확인하지 않았다"고 명시했으므로 전부 다시 읽었다. 문서의 가정과 실제가 다른 곳:

| 문서의 가정 | 실제 코드 | 결정 |
|---|---|---|
| ACTIVE/PARKED/CANCELLED/PROMOTED 같은 상태명 | 그런 enum은 없다. 변경안은 `PROPOSED/APPLIED/DISMISSED/CONFLICT/STALE/EMPTY` | 기존 명명을 따르고 정리안에는 `PROPOSED/APPLIED/DISMISSED/SUPERSEDED/EMPTY` |
| MariaDB 10.4 | 맞다(클라이언트만 MySQL 8.0) | 생성 컬럼 + UNIQUE로 부분 유일 인덱스를 흉내 내는 기존 방식(`proposed_guard`)을 그대로 쓴다 |
| 자료별 변경안이 트리 버전을 공유 | 맞다. `TopicChangeProposalService.apply`가 적용 후 같은 프로젝트의 다른 열린 변경안을 STALE로 내리고 `analysisJobService.retryLink`로 **다시 등록**했다 | 이 되풀이를 없애는 것이 이번 작업의 핵심(§3) |
| — | `ProposedTopicIndex`가 자료별 변경안을 읽어 **같은 제목끼리 합치고** 있었다. 학습 지도와 계획 자료 선택이 그것을 쓴다 | 원본만 정리안으로 바꾼다. 합치는 코드는 없앤다 — 이제 모델이 만들 때 이미 합친다 |
| — | LINK 분석이 **과제-프로젝트 연결**을 곁들여 하고 있었다 | LINK를 끄면 생기는 구멍이다. AI 없는 별도 단계로 옮겼다(`AssignmentProjectAttacher`) |
| — | `TopicTreeEditor.apply`가 `materialId` **하나**를 받는다 | 구간이 자기 자료를 알고 있으므로(`MaterialSection.materialId`) 구간마다 풀도록 고쳤다. 기존 호출자는 그대로 동작한다 |
| — | 소요 시간을 남기는 표가 없다 | 예상 시간을 말할 근거가 없다 → `material_analysis_timings` 신설 |
| 초안 버리기 후 일정 탭 이동 불가 | **이미 고쳐져 있다**(API `db53f34`, UI `d5e773e`, 2026-09-20). 회귀 테스트도 있다(`proposalTab.test.js`) | 다시 고치지 않는다. 새 정리안 화면이 같은 실수를 하지 않는지만 테스트로 고정했다 |

## 2. 왜 "변경안을 합쳐 실행"이 아닌가

지시 문서가 이미 지적한 것이고, 코드를 읽어 보니 그대로였다.

강의 슬라이드가 「스택」을, 교재가 「스택 자료구조」를, 실습 안내가 「스택 구현」을 만든다. 자료별로는
셋 다 옳다. 순서대로 실행하면 중복 항목 셋이 남는다. 이것은 트랜잭션 하나로 묶는다고 풀리지 않는다 —
**같은 것을 가리키는지 판단하는 일**이고, 그 판단에는 세 자료를 같이 봐야 한다.

그래서 정리안을 프로젝트 단위로 만든다. 실측(§4.2)에서 실제로 그렇게 동작했다.

## 3. 되풀이를 끊은 자리 셋

1. **생성**: `MaterialAnalysisJobService.enqueueLink`·`registerLinkBacklog`·`retryLink`가
   `material.analysis.link-jobs.enabled`(기본 false)를 본다.
2. **실행**: `TopicLinkAnalyzer.analyze` 입구에서 취소. 전환 직전에 선점된 작업이 뒤늦게 와도 막힌다.
3. **저장**: `TopicChangeProposalService.create` 입구에서도 막는다. 실행을 우회해 온 결과도 행을 남기지 않는다.

그리고 적용 경로에서 `retryLink` 호출을 없앴다. 다른 열린 변경안을 STALE로 내리는 것은 남겼다 —
그것은 사실이기 때문이다(옛 트리 기준이다).

셋을 다 막은 이유: 하나만 막으면 나머지 경로로 새 변경안이 생기고, 그것은 이제 **어느 화면에서도
적용할 수 없는** 행이다. `ProjectTidyLegacyTransitionDbTest`가 세 곳을 각각 본다.

### 4.2 실제 모델 평가

스크립트 `scripts/ai-baseline/verify-project-tidy-2026-09-21.py`. 서버 8081 + **격리 DB
`memo_tidy_verify`**(스키마만 복제한 빈 DB), 합성 계정과 스크립트가 만든 합성 자료(.sh 평문)만 썼다.
**사용자의 실제 자료·계정으로는 평가하지 않았다.**

자료 셋은 같은 개념을 일부러 다른 이름으로 다룬다:
강의 노트(「스택」「큐」) · 교재 목차(「3.1 스택 자료구조」「3.3 큐 자료구조」「3.4 원형 큐」) ·
실습 안내(「스택 구현 연습」「괄호 검사기」「원형 큐 구현」).

| 회차 | 관찰 |
|---|---|
| 1차 | 예상 35~80초 → 실제 40초. 정리안 생성 14초. **ADD 1개**(「스택과 큐의 구조 및 연산」)에 강의+교재 구간이 함께 붙고 실습이 하위 둘로 |
| 2차 | 예상 36~59초 → 실제 16초. 생성 10초. **ADD 2개**(「스택(Stack)」「큐(Queue)」), 각각 강의+교재 구간을 함께 인용. 근거에 "강의 S1995와 교재 요약 S1994가 … 하나의 학습 항목으로 구성한다" |
| 3차 | 생성 12초. **ADD 4개**(상위 1 + 하위 3), 그중 3개가 두 자료의 구간을 함께 인용 |

세 회차 모두 **자료 수만큼 항목이 생기지 않았고**, 한 변경이 두 자료의 구간을 함께 인용했다 —
이것이 확인하려던 것이다. 다만 회차마다 묶는 층위가 달랐다(1차는 「스택과 큐」 하나 + 하위 둘,
2차는 「스택」「큐」 둘, 3차는 상위 하나 + 하위 셋). 어느 쪽이 더 낫다고 판정할 기준을 이 검증은
갖고 있지 않다. **반복 3회는 제한적 점검이지 품질 입증이 아니다.**

**예전 방식이 무너지던 자리**(트리가 이미 있는 상태에 같은 개념의 자료가 더 들어옴)는 3차의 2단계에서
따로 봤다. 4주차 퀴즈 자료를 추가하고 다시 정리를 요청했더니:

```
[ADD]  「스택과 큐의 구조 및 연산」 아래에 「괄호 검사기」      (기존 트리에 없는 것만)
[ADD]  「스택과 큐의 구조 및 연산」 아래에 「원형 큐 구현」
[LINK] 「스택과 큐의 구조 및 연산」에 lecture-week3.sh 연결
[LINK] 「스택과 큐의 구조 및 연산」에 textbook-ch3.sh 연결
[LINK] 「스택과 큐의 구조 및 연산」에 quiz-week4.sh 연결      ← 새 자료는 기존 항목에 붙었다
[LINK] 「스택 구현 연습」에 lab-week3.sh 연결
ADD 2 · LINK 4
```

**「스택」을 또 만들지 않았다.** 근거도 "…기존 개념 항목에 연결합니다"로 적혔다. 자료별 변경안이었다면
여기서 네 번째 「스택」 제안이 나오고, 적용하는 순간 나머지가 다시 분석됐다.

토큰·금액은 집계하지 않았다(이 경로의 사용량이 API로 노출되지 않는다). 호출 수는 회차당 자료 분석
3~4회 + 정리 1~2회다.

### 4.5 검증하지 못한 것 · 주의

- **UI 테스트의 부하 민감성**: 작업 중 UI 스위트를 API 스위트·서버·모델 검증과 <같은 머신에서

  CPU 경합이었다. 그래도 그중 둘은 진짜 5초 시간 초과였으므로 `vite.config.js`의 `testTimeout`을
  15초로 올려 두었다 — **느린 것을 통과시키려는 값이 아니라 부하에 따라 결과가 달라지는 것을
  줄이려는 값이다.** 최종 수치는 조용한 머신에서 잰 것이다.
- 실제 LLM으로 본 것은 §4.2의 세 회차(빈 트리 2 + 기존 트리 1)뿐이다. 입력 한도 초과(부분 정리), 모델 실패 뒤 재시도,
  판 교체 시 편집 승계는 **고정 응답·DB 테스트로만** 확인했다.
- 하루 한도에 닿은 상태의 화면은 실제로 만들지 않았다(단위 테스트의 고정 값으로만 확인).
- 배포 환경에서 돌려 보지 않았다. 원격 push·PR·배포는 하지 않았다.

  - **기존 행 변경 1건**: 열린 자료별 변경안 128행이 `PROPOSED` → `SUPERSEDED`

    맨 아래에 있다.
  - LINK 작업 `QUEUED`/`PAUSED`: 0행(이미 전부 끝나 있었다).
  - 다른 표의 행 수는 바뀌지 않았다.
- 검증용으로 만든 것(정리는 사용자 판단):
  - DB `memo_tidy`(2026-09-21 `memo` 전체 복제 — 마이그레이션 재실행 확인용),
    `memo_tidy_verify`(스키마만 복제한 빈 DB — 실제 모델 평가용). 지우려면 `DROP DATABASE`.
  - `memo_tidy_verify`의 합성 계정 `project-tidy-*@example.com`(비밀번호 `tidy-1234`).
  - 업로드 파일은 저장소 밖 임시 디렉터리에 두었다(`--storage.materials.upload-dir`).
- 푸시·PR·배포: 하지 않았다.

## 6. 배포 순서

1. `docs/sql/2026-09-21-project-tidy.sql` 적용. 추가형이고 재실행할 수 있다.
   §5의 "기존 행 변경 1건"을 먼저 읽는다.
2. 서버 배포. 마이그레이션 없이 새 서버를 올리면 뜨지 않는다(새 표를 읽는다).
   반대(옛 서버 + 새 스키마)는 안전하다 — 새 표를 모른 채 동작한다.
3. 화면 배포. **옛 화면 + 새 서버**도 동작한다: 자료별 변경안 목록은 빈 배열이 오고,
   업로드는 `batchItemId` 없이도 그대로 된다(묶음 없이 올라간다).
4. 되돌리려면 화면 → 서버 순으로 내리고, 마이그레이션은 굳이 되돌리지 않아도 된다
   (옛 서버는 새 표를 보지 않는다). 자료별 변경안을 되살리려면 SQL 파일의 롤백 UPDATE를 쓴다.

## 7. 남은 한계

- 입력 한도를 넘는 프로젝트에서 **구간을 자른다**. 잘랐다는 사실·못 본 수는 저장하고 화면이 말하지만,
  "전체를 훑고 필요한 부분만 다시 읽는" 2단계 조회는 만들지 않았다. 자료가 수십 개인 프로젝트에서는
  부분 정리가 잦을 수 있다.
- 정리안 생성은 모델 호출 **1회**다. 큰 프로젝트를 분할해 판단하고 합치는 경로는 없다.
- `dependsOn`은 지금 관계가 하나뿐이다(새 항목 아래 새 항목). 병합·분할은 실행 순서로 풀리므로
  선택 관계가 생기지 않는다 — 다른 의미 충돌이 발견되면 여기 추가해야 한다.
- 예상 시간은 표본이 쌓여야 쓸 만해진다. 지금 `memo`에는 표본이 0이라 첫 사용자는 기본값
  (청크당 20~50초)을 본다. 화면이 "초기 추정"이라고 말한다.
- 묶음 상태를 옮기는 쓰기가 **조회 경로**에 있다(`MaterialAnalysisBatchService.get`). 별도 폴러보다
  단순하지만, 아무도 조회하지 않으면 끝난 묶음이 `ANALYZING`으로 남는다(응답은 FINISHED로 나가므로
  화면은 옳다).
- ZIP 가져오기는 묶음에 들어가지 않는다. 안에서 꺼낸 자료는 각자 분석 대기에 들어가지만 묶음 진행
  카드에는 보이지 않는다.
