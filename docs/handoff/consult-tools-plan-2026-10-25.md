## 1. 현재 코드의 사실과 이전 보고와 다른 점

### 1-1. 확인한 사실

**F1. 상담 턴 = 구조화 출력 한 번**
- 모델은 답변 → `<<<AI_STRUCTURED>>>` → JSON 하나를 낸다.
- Spring AI `2.0.0`이다. 상담 경로에 도구 호출(`@Tool`, `ToolCallback`, `.tools(`)이 없다.
- 유일한 다회 호출은 자료 "추가 읽기"다. 턴당 최대 2회 모델 호출이다.
  - `AiConversationService.subscribeRound` / `startReadMoreRound`
  - 1회차 텍스트는 이미 스트리밍된 뒤 화면에서 지워진다.
- `spring.ai.retry.max-attempts=1`이다. 실패한 멱등 키는 재시도할 수 없다.

**F2. 사용 한도는 호출 행 수로 센다**
- `ai_usage_logs`의 `feature='AI_CONSULTATION'` 행 수다. 하루 50, 한 달 1000.
- 추가 읽기 2회차(`AI_CONSULTATION_READ_MORE`)는 세지 않는다.

**F3. 상담 턴의 단계별 기록 테이블이 없다**
- 프롬프트, 1회차 출력, 원 JSON은 저장되지 않는다.
- 계획 생성에만 `plan_generation_traces`가 있다.

**F4. 턴의 부가 결과는 한 트랜잭션으로 저장된다**
- `completeTurnSuccess`에서 메시지·제안·일정 후보·기억 후보·draft·합의를 함께 저장한다. 계약 위반이면 턴 전체가 롤백된다.
- `consult_json`(질문 카드·해석)은 트랜잭션 밖에서 저장된다. 실패해도 무시된다.
- 재접속 시에는 저장된 결과를 다시 내보낸다. 모델을 재호출하지 않는다.

**F5. 일정 후보는 생성 두 종류뿐이다**
- `COMMITMENT`, `ROUTINE`만 있다.
- 상담 프롬프트의 등록 일정 줄에는 id가 없다. "다시 만들지 말고 피하라"로만 쓰인다(`AiWorkspaceContextBuilder.appendFixedRealityLines`).

**F6. 가용시간 계산은 DB만 읽는다**

- 회차 하나를 없는 것으로 계산할 방법이 없다.

  - 밤 9시에 말하면 남는 시간이 0이 되고, 예산은 최소값 5분이 된다(코드 추론).

- 약속을 삭제하면 파생 이동이 고아로 남는다(코드 추론).

## 2. 사용자 요청부터 적용까지의 흐름

예: 사용자가 "오늘 쿠팡 근무 빼고 8시까지 공부 잡아줘"라고 말한다.

```text
[턴 준비]   기존 그대로: 대화 잠금, 멱등 키, 사용 한도(턴당 1로 셈)
   │
[도구 단계] 텍스트를 스트리밍하지 않는다. 진행 표시 이벤트만 보낸다("일정 확인 중…")
   │  모델 ↔ 서버 도구 실행기 (서버가 매 호출을 실행·검증·기록. 상한 적용)
   │   1. schedule.find(오늘, "쿠팡")
   │        → routine 220 회차(10/25 17:00~10/26 02:00)
   │          + 인접 이동 후보 218(15:30~17:00), 219(10/26 02:00~03:30)
   │   2. change.propose(RoutineOccurrenceSkip{220, 2026-10-25})
   │        → OK, 효과: 그 회차가 바쁜 시간에서 빠짐
   │        이동 후보는 별도 항목으로 제안: "함께 뺄까요?"
   │   3. studyTime.set("8시까지" 원문 인용)
   │        → 서버가 해석: 오늘 ~20:00, 시작은 지금. 근거 구절 유지
   │   4. availability.preview(오늘, 묶음 반영 / 미반영)
   │        → 근무 유지 시 남는 시간 N분(지금~15:30), 제외 시 M분(이동시간 15:30~17:00은 별도 항목)
   │        "17~20시가 근무와 겹친다" 같은 실제 원인을 서버가 계산
   │   (상한 도달·오류 → 확인한 것 / 못 한 것을 구분해 다음 단계로)
   │
[답변 단계] 기존처럼 답변 스트리밍 + 구조화 JSON (기억·합의·질문 카드 등 유지)
   │  프롬프트에 "확정된 묶음 상태와 판정"을 싣는다. 이 단계 전에 검증이 끝나 있으므로
   │  스트리밍되는 설명이 검증 전 성공을 단정할 일이 없다. 카드는 서버가 저장된 묶음으로 그린다
   │
[턴 완료 트랜잭션] 메시지 + 변경 묶음(PROPOSED) + 기존 부가 결과를 함께 저장
   │  실패하면 함께 롤백된다. 단계별 기록은 별도로 남는다(성공·실패 무관)
   │
[검토] 상담 패널의 변경 묶음 카드: 항목 체크, 의존 표시, 시간 조건 상태
   │  "이 조건으로 계획 초안 만들기" (= 초안 생성 요청. 원본 적용 아님)
   │
[초안 생성] 기존 기간 계획 생성기. 입력 = 원본 + 이 묶음의 선택 항목(가정 상태) + 시간 조건
   │  분량 예산, 모델 입력의 "등록된 일정·남는 시간", 근거 지문, 재생성, 배치 후보 모두 같은 가정 상태로 계산
   │  초안은 "기대는 변경: 묶음 #k의 항목 i"를 기록한다
   │
[적용] (a) 계획 확정 = 기대는 묶음 항목 + 계획을 한 트랜잭션으로 적용
       (b) 묶음만 적용(계획 없이 근무만 빼기)도 가능
   │  적용 직전: 대상 잠금 → 각 항목 최신 검증 → 계산 근거 지문 비교
   │  다르면 409 STALE + 무엇이 달라졌는지 → "다시 검토"
   │
[부분 거절] 근무 제외를 해제하면, 그 항목에 기댄 계획 초안은 "재계산 필요"가 된다
            적용 버튼이 막히고 [이 조건으로 다시 만들기]만 남는다
```

**"오늘 8시까지 공부 잡아줘"만 말한 경우**
- 묶음을 만들지 않고 원본 기준으로 계산한다. 근무가 17시에 시작하므로 공부 가능 구간은 지금~17시이고, 17~20시는 근무와 겹친다.
- 분량이 모자라거나 충돌이 있을 때만 대안 카드를 낸다. 예: "17~20시는 등록된 근무와 겹쳐요. 지금~17시에 N분을 잡았어요. 오늘 근무를 뺀 안도 볼까요?"
- 이 대안은 서버가 계산한 실제 원인(어느 일정이 몇 분을 차지하는지)에 근거한다.

## 3. 책임 경계

```text
ai/turn (공통 상담 실행부)    ← 도메인을 모른다
  · 도구 단계 루프(라운드·도구 수·시간·토큰 상한), 도구 디스패치, 인자 역직렬화·검증 오류의 결과 코드화
  · 단계별 기록(새 테이블), SSE 진행 이벤트, 답변 단계 프롬프트에 묶음 판정 싣기
  · 등록된 도메인 모듈의 도구 목록 → 모델 도구 정의 + "지원 기능 목록" 문서 자동 생성

ai/change (공통 변경안 처리부)
  · 변경 묶음·항목 저장(상태, 의존, 계산 근거 지문), 화면 DTO, 선택·해제
  · 적용 오케스트레이션: 한 트랜잭션, 잠금 순서 고정, 항목별 최신 검증 → 도메인 apply
  · 계산용 상태 구성: 묶음 항목 중 "시간 효과"를 가진 것만 겹쳐 놓는다

scheduling (가정 상태의 계산)
  · AvailabilityEstimateService를 "사실 읽기(DB)"와 "순수 계산"으로 나눈다
  · 순수 계산은 사실 + 겹침(회차 제외·이동, 약속 취소·변경, 실행 항목 시간 변화) + 시간 조건을 받는다
  · 기존 호출부는 겹침 없는 같은 결과를 받는다(동작 보존)

도메인별 AI 연결 모듈 (데이터를 소유하는 패키지 안, 예: routine/ai, commitment/ai, execution/ai, assignment/ai)
  · 그 도메인의 조회 도구, 대상 찾기, 변경 op(타입이 있는 record)
  · op마다: 검증(가정 상태 기준) → 결과 코드, 적용(기존 서비스 호출), 적용 직전 최신 검증
  · 선택 능력은 별도 인터페이스: 시간 효과(일정·실행만), 연결 항목 제안(근무 → 이동)
  · 기존 서비스의 업무 규칙은 바꾸지 않는다. 필요한 읽기·잠금 보조 메서드만 추가한다
```

**정하지 않는 것**
- 범용 CRUD나 Map으로 통일하지 않는다.
- 모든 도메인에 시간 효과나 되돌리기를 의무화하지 않는다.
- 별도 에이전트를 두지 않는다. 상담 모델 하나가 도구를 쓴다.

**새 도메인(예: 가계부) 추가 방법**
- 그 패키지에 모듈 빈 하나와 op 타입을 추가한다.
- 중앙 루프와 묶음 처리 코드는 바꾸지 않는다. 화면 카드는 op별 요약 문구로 그린다.

**결과 코드(공통)**
- 대상: 찾음 / 없음 / 여러 개(후보 목록) / 조회 실패
- 상태: 이미 처리됨 / 충돌(무엇과)
- 오류: 입력 오류(모델 인자) / 서버 오류
- 시간 조건: 시간 조건 없음 / 해석 모호 / 검증 실패 / 다른 일정과 충돌 / 요청량이 들어가지 않음

### 4-2. 해결 방향

원문 근거는 유지하고, "한 문장에 정확히 하나"라는 판정 방식을 고친다.

1. **시간 조건을 구조로 둔다(`StudyTimeCondition`).**
   - 공부 가능 구간(여러 개, 날짜가 붙은 시각) / 제외 구간(식사 등) / 총 공부량(분, 하루·계획 전체) / 의도(채움·가용)
   - 부분마다 원문 인용, 해석 메모(예: "오전·오후를 말하지 않아 오후로 봄"), 상태 코드를 붙인다.
   - 합의(planBrief)에 구조로 저장한다. 꼬리표 텍스트에 의존하지 않는다. 기존 TIME_BUDGET 항목은 읽기 호환만 유지한다.
2. **부분별 원문 검증으로 바꾼다.**
   - 모델은 구간·제외·분량을 각각 인용과 함께 낸다. 서버는 각 부분의 값이 **그 인용에서** 읽히는지 확인한다.
   - 한 문장에 시각이 여럿이어도 역할별로 검증되니 T5가 해결된다. 같은 시각을 두 역할에 쓰거나 인용에 없는 값을 쓰면 검증 실패다.
   - 파서는 붙여 쓴 `~`/`-` 구간을 읽게 고친다(T6). 소수점·분수 안쪽 보호 규칙은 유지한다.
3. **기준 시각을 "그 말을 한 시각"으로 바꾼다(T3, T12).**
   - 오전·오후 후보는 "그 날 공부 시간으로 말이 되는가"로 고른다. 기준은 발언 시각과 계획 날짜다.
   - 둘 다 그럴듯하면 모호로 판정하고 묻는다. 고른 해석은 화면에 밝힌다.
   - 시작이 이미 지났으면 조건은 유지한다. 실제 배치만 지금 이후로 제한하고 "2시가 지나 지금부터 배치"라고 이유를 보여 준다.
4. **단위 판정(T4)**
   - 하루짜리 계획에서는 하루 몫과 전체 몫이 같으므로 단위 말이 필요 없다.
   - 여러 날 계획에서만 모호로 판정하고 묻는다.
5. **나중 발언(T7)**
   - 모델이 새 시간 발언을 추가·정정·제외·무관 중 하나로 분류하고 인용을 붙인다. 서버가 검증한다.
   - 시간 표현이 또 나왔다는 이유만으로 기존 조건을 버리지 않는다. 정정이면 해당 부분만 바꾸고 이력을 남긴다.
6. **자정 넘김·기본 창 밖(T8, T9)**
   - 구간은 날짜가 붙은 시각으로 저장한다. "새벽 1시까지" = 다음 날 01:00.
   - 사용자가 명시한 구간은 그날의 기본 창을 대체한다. 실제 일정은 계속 뺀다.
   - 자정 이후 부분의 배치 방식은 §8 결정 사항이다. 어떤 경우든 조용히 자르지 않고 이유를 보인다.
7. **가용 범위와 공부량을 구분한다(T10).** 분량을 말하면 그 값이 목표다. 시간대만 말한 경우의 기본값은 §8 결정 사항이다.
8. **탈락을 숨기지 않는다(T11).**
   - 최근 발언에 시간 표현이 있는데 조건이 "채택"이 아니면, 초안 생성 카드(OFFER)와 초안 화면에 상태와 원문을 보인다.
   - 모호하면 생성 전에 묻는다.
   - 검증에 실패하면 "말한 시간을 확인하지 못했어요(원문…, 이유…)"를 보이고 [기본 시간으로 만들기 / 다시 말하기]를 고르게 한다.
9. **판정 경로를 하나로 묶는다.**
   - 상담 도구(`studyTime.set`)와 계획 화면 경로(범위 추출 `PlanScopeExtractor.studyTime`)가 같은 해석기·검증기와 같은 타입을 쓴다.
   - 상담에서 채택한 조건이 있으면 그것이 우선이다. 범위 추출이 다른 값을 읽으면 덮지 않고 "불일치"로 표시한다.
10. **같은 조건을 끝까지 쓴다.**
    - 예산(`userTimeOf`), 모델 입력, 근거 지문, 재생성 문맥(`PlanRequestContext`), 배치(`PlanStudyTimeResolver` → 조건의 구간·제외), 확정 검증이 같은 조건을 쓴다.
    - 제외 구간은 배치 후보에서 빠진다.

## 9. 반론과 구현 부담

**지연·비용**
- 도구 단계가 턴당 모델 호출을 2~5회로 늘린다. 첫 글자가 나오기까지 시간이 길어진다.
- 대응: 진행 표시, 상한, 작은 도구 결과, 낮은 reasoning effort. S6에서 측정한다.

**모델의 도구 사용 품질은 미검증**
- 현재 모델 설정(`ai.consultation.model`)의 도구 호출 품질은 확인한 적이 없다.
- 실패 시에도 "확인한 것 / 못 한 것"을 구분해 답하도록 실행기가 보장한다.

**가정 상태 누락 위험**
- 겹침을 한 소비자에서 빠뜨리면 미리보기와 확정이 어긋난다.
- 대응: 사실 읽기 지점을 하나로 모으고, 소비자 목록을 테스트로 고정한다.

**규모**
- 백엔드 4개 영역과 UI 2개 화면에 걸친다. 커밋 7개 안팎이다.
- 단계마다 독립 검증이 가능하게 나눴지만 브랜치가 길게 산다.

**B 대비**
- 서버 고정 순서(B)가 더 싸고 예측 가능하다.
- C를 택한 이유는 사용자가 원하는 "찾아보고, 안 되면 다른 방법을 제안"하는 경험이다. 이를 위해 도구 단계와 묶음 처리의 이중 구조를 감수한다.

## 11. 사용자 보완(2026-10-25) — 확정 사항

1. **실호출 선검증(S0.5).**
   - S0 직후, 현재 상담 모델·API(Spring AI 2.0 + `ai.consultation.model`)로 최소 흐름을 실제 호출로 확인한다.
   - 흐름: 일정 조회 → 오늘 회차 제외 제안 → 가정 상태 가용시간 계산 → 결과 설명.
   - 성공 여부·지연·호출 수를 기록한다. 실패하면 도구 정의·실행 방식을 조정한 뒤 S1으로 간다.
   - S6은 전체 시나리오다.
2. **시간 꼬리표 문제는 현재 커밋 소스로 재현한다.**
   - 현재 소스에서 단위 테스트로 재현한다. 이전 빌드 산출물(jshell) 결과와 구분해 보고한다.
   - 세 가지를 분리한다: **사용자 원문 근거**(인용·발언 id) / **해석된 시간 조건**(구조) / **화면 표시 문구**(파생값).
   - 표시 문구는 저장하더라도 원문 검증의 입력이 되지 않는다.
3. **묶음은 확정 전까지 가정이다.**
   - 원본 일정·실행 상태, 장기 기억(user_contexts), 합의의 확정 사실에 반영하지 않는다.
   - 상담 기억 자동 저장(`ConsultTurnService.finish` → `UserContextService.autoSave`)이 "오늘 근무 뺌" 같은 미확정 변경을 STATED 사실로 저장하지 않도록 확인하고 막는다.
   - 묶음 항목을 수정·해제하면 의존 항목과 그 묶음에 기댄 초안을 다시 검증한다. 초안은 재계산 필요로 표시하고 확정을 막는다.
4. **최종 적용 = 원자성 + 중복 방지 + 동시 변경 대응.**
   - 적용 요청에 멱등 키를 둔다. 같은 키로 재시도하면 저장된 결과를 돌려준다.
   - 묶음 헤더 상태는 조건부로 전이한다(PROPOSED → APPLIED는 한 번만).
   - 검증과 저장을 같은 트랜잭션 안에서, 대상 잠금(반복 일정 부모 행·약속·실행 version 조건 갱신)을 잡은 뒤 한다.
   - 계산 근거 지문(영향 범위의 busy·대상 version)을 잠금 이후 다시 계산해 비교한다.
   - 검증 대상: 중복 클릭, 응답 유실 후 재시도, 다른 요청의 동시 수정.
   - 모델 호출과 사용자 대기는 DB 트랜잭션 밖에서 한다(도구 단계의 조회·검증은 짧은 읽기 트랜잭션).
5. **D1 확정: 시간 범위와 공부량을 구분한다.**
   - "2시부터 8시까지 공부 잡아줘" → 그 범위에 배치한다. 화면에는 **공부 범위 / 휴식·제외 / 실제 공부량**을 따로 보여 준다.
   - "그중 총 4시간"처럼 분량을 명시하면 범위 안에서 그 분량을 목표로 한다.
   - 모호하거나 충돌할 때만 필요한 부분을 묻는다. 예: 범위보다 분량이 큼, 오전·오후 모호, 여러 날 단위 모호.
   - 명시 조건을 조용히 기본값으로 대체하지 않는다.
   - 범위만 말한 경우의 실제 공부량: 범위 안의 남는 시간에서 휴식 규칙(기존 항목 사이 여유)을 뺀 값을 목표로 한다. 계산 근거를 함께 보인다.
6. **D2~D4는 권장안대로 확정.**
   - 추정한 이동시간 관계는 기본 미선택이다.
   - 기존 제안 적용 경로(일정 후보·실행 조정 제안·계획 확정)도 이번에 추가하는 검증을 우회하지 않는다. 예: 묶음이 있는 대상의 기존 경로 적용 → 묶음 재검증.
   - D5 상한은 초기값으로 쓴다(모델 6회, 도구 12회, 120초, 한도 턴당 1).
   - 초과·시간 초과·도구 실패 시 원본을 변경하지 않는다. 처리 상태(확인한 것 / 미완료)를 정확히 안내한다.
7. **리뷰 관점(코드 리뷰 때 명시적으로 확인).**
   - 공통 실행부에 영역별 분기가 늘지 않는가.
   - 미리보기와 확정이 같은 변경 의미(같은 op 타입의 효과·검증 코드)를 쓰는가.
   - 일반화는 일정·실행·과제 실제 구현이 요구하는 만큼만 한다.

## 12. Codex 계획 리뷰 1회차 반영 (REVISE → 수정)

1. **미리보기 경로 포함.**
   - 묶음 리비전과 시간 조건을 다음 경로에 연결한다:
     - `SchedulePreviewService`의 계산·저장·재조회
     - UI 미리보기 캐시 키(`previewSolveCache.js`)
     - 주간 미리보기(`PlanWeekPreview.jsx`, 원본 일정 별도 조회)
   - 제외·이동 예정 회차는 "예정" 표시와 함께 가정 상태로 그린다. S5 범위다.
2. **불변 `ScenarioSnapshot` 하나를 모든 계산 경로에 넘긴다.**
   - 내용:
     - 원본 사실: busy, 다음 수업·마감 근거, 기존 실행 항목 목록, 과제 마감·완료
     - 시간 조건
   - 생성기(1467행 부근 다음 수업·기존 항목 조회 포함), 미리보기, 배치, 확정 검증이 같은 스냅샷 생성기를 쓴다.
   - op별 투영표는 아래와 같다. 회차 식별자는 항상 `routineId + sourceDate`다.

   | op | 투영 |
   |---|---|
   | 회차 SKIP | 그 회차 busy·다음 수업 후보에서 제거 |
   | 회차 MOVED | 원래 회차 제거 + 이동 회차 추가 |
   | 회차 복원(예외 삭제) | 예외 효과 제거 |
   | 반복 일정 생성 | 범위 내 회차 생성 |
   | 반복 일정 수정·종료일 | 새 규칙으로 재전개. 기존 예외 충돌이면 op 거절 |
   | 약속 생성 / 수정 / 취소 | busy 추가 / 이동 / 제거 |
   | 실행 완료·부분 수행·보류·복귀·배치 해제·이동·축소 | 기존 실행 목록과 TIME_FIXED busy 갱신 |
   | 과제 마감 정정 / 완료 | 마감 근거·과제 목록 갱신 |

   - 한 묶음 안에서 같은 대상에 충돌하는 여러 op는 **거절한다**(1차 단순화).
3. **검토 내용 고정 계약.**
   - **리비전**: 묶음에 `revision`을 둔다. 선택 변경·항목 수정·적용 요청은 기대 리비전을 받고, 서버가 잠금 아래 비교한다(409).
   - **초안 스냅샷**: 초안에 저장하는 것: 묶음 리비전, 선택 항목과 의존 관계, 정규화된 op 내용, 시간 조건의 불변 스냅샷.
   - **멱등 키**: (사용자, 작업 종류)에 묶고 요청 해시를 저장한다. 같은 키에 다른 내용이 오면 409.
   - **부분 적용**: 선택한 항목만 적용하고, 미선택 항목은 DISMISSED로 닫는다. 묶음은 APPLIED로 끝난다(재사용하지 않는다).
   - **묶음만 먼저 적용한 뒤 계획 확정**: 초안 스냅샷의 리비전과 선택 항목이 적용된 결과와 같으면, 확정 때 "이미 적용됨"으로 인정한다. 이때도 최신 상태가 op 효과와 일치하는지 검증한다.
   - **같은 묶음에 기대는 초안 둘**: 묶음이 바뀌거나 다른 선택으로 적용되면 불일치하는 초안은 재계산 필요가 된다.
   - **적용 결과 저장**: 생성된 예외 id, 실행 기록 id, 계획 버전 id와 재응답 본문을 적용 트랜잭션에서 함께 저장한다.
4. **잠금·지문.**
   - version이 없는 반복 일정은 제안 시점의 **전체 상태 해시**(본체·요일·예외)를 보관하고, 잠근 최신 상태와 비교한다.
   - 새 약속의 동시 삽입은 `PlanConfirmScheduleGuard`의 범위 잠금 조회(`FOR UPDATE`)를 재사용해 막는다.
   - 순서를 고정한다:
     1. 영향 범위 전체 잠금(약속 → 실행 → 반복 일정. 기존 경로와 같은 순서)
     2. 적용 전 원본 지문 비교
     3. op 적용
     4. 최종 상태 검증
5. **소유권.**
   - 인증 사용자 id는 모델 인자에 없다. 서버 실행 문맥으로만 전달한다.
   - 조회·제안·미리보기·선택 변경·적용·기록 조회 모두 소유권을 검사한다.
   - 중첩 id도 검사한다: 예외↔반복 일정, 항목↔묶음, courseId 소유·활성(예: 실행 생성의 courseId).
   - 타 사용자 id를 넣는 통합 테스트를 만든다.
6. **인젝션.**
   - 도구는 조회와 **턴 작업 공간의 임시 제안**만 한다. 시간 조건·묶음은 턴 완료 트랜잭션에서만 저장한다.
   - 사용자 조건의 근거는 서버가 소유를 확인한 사용자 발언 id와 그 안의 인용 범위로 검증한다.
   - 자료에서 유래한 내용은 사용자 진술이나 승인으로 승격하지 않는다(기존 자료 턴 제한과 같은 규칙을 도구 단계에도 적용).
   - 답변 단계에서는 도구를 제거한다.
   - 도구 모드 턴에서는 기존 `scheduleSuggestions`·`adjustments`를 막는다. draft 승격은 묶음으로 보내 중복을 없앤다.
   - 적용·승인 도구는 모델에 노출하지 않는다.
7. **시간 조건 순서·수량.**
   - 순서를 고정한다: 조건 해석 → 스냅샷 → 가용시간·예산 → 생성.
   - 기본 창에서 0분이라고 조건을 읽기 전에 조기 종료하는 것(573행)과 0→5분 보정(`userTimeOf`)을 고친다.
   - **요청량·수용량·배치량을 분리해 저장·표시한다.** 부족분이나 항목 상한 때문에 요청량을 축소하지 않는다.
   - 확정 때 클라이언트 편집을 병합한 최종 항목 전체가 범위·제외 구간·상호 비충돌을 만족하는지 검사한다.
   - 휴식 규칙: 범위만 말한 경우의 목표 공부량 = 범위 안 남는 시간 − 휴식. 휴식은 연속 공부 60분마다 10분으로, 예산에 명시적으로 차감하고 근거로 표시한다. 솔버의 15분 간격 SOFT 선호는 그대로 두고, 실제 배치량이 목표보다 적으면 차이를 표시한다.
8. **자정.**
   - "새벽 1시까지"의 날짜는 발언 시각과 명시된 오늘·내일·날짜로 해석한다. 21시 발언 → 다음 날 01:00. 00:30 발언 → 그날 01:00.
   - 실행 항목은 자정을 넘지 않는다. 대신 **종료가 다음 날 00:00 정각인 경우만 허용**하도록 `validatePlacement`를 확장한다(DB 제약도 확인).
   - 자정 이후 부분은 다음 날짜 항목으로 분할한다.
   - 요청 기간(하루)과 실제 배치 종료(다음 날 01:00)를 구분한다. 하루 분량이 두 번 계산되지 않게 한다.
9. **S0.5에서 API와 예산을 확정한다.**
   - Spring AI 2.0에서는 1.x의 내부 도구 실행 토글이 사라졌다는 지적이 있다. 2.0.0 실제 의존성으로 "모델은 도구 호출만 내고, 서버가 직접 실행하는" 방식을 선검증한다.
   - 상한(모델 6회)에는 최종 답변 호출을 포함한다. 기억 보조 추출 호출은 별도로 기록한다.
   - 같은 응답의 도구 호출은 받은 순서대로 순차 실행한다.
   - `ai.request.timeout-seconds`와 stale 잠금 기준을 120초 전체 마감에 맞춘다.
   - 취소·시간 초과 뒤 늦게 완료돼도 묶음이 저장되지 않는지 테스트한다.
10. **검증 추가**: 다른 탭의 선택 변경, 같은 키 다른 요청, 동시 새 일정 삽입, version 없는 반복 일정의 제목 변경, 타 사용자 id, 악성 자료가 시간·합의 변경을 유도하는 경우, 0분 가용시간, 정확한 자정 종료.
11. **§2 예시 수정**: 17시 근무와 "8시까지"의 관계를 바로잡았다.

## 13. Codex 계획 리뷰 2회차 반영

1. **잠금 목록 = 계산에 쓴 모든 의존 데이터.**
   - 변경 대상뿐 아니라 스냅샷 계산에 쓴 과제와, TIME_FIXED가 아닌 실행 항목까지 잠근다.
   - 지문은 **잠금 조회 결과로** 다시 만들어 비교한다.
   - 순서: 약속 → 실행 → 반복 일정 → 과제.
   - 경합 테스트: 지문 비교 후 확정 커밋 전에 참조 과제의 마감을 바꾸는 요청이 오면, 그 요청이 기다리거나 확정이 STALE이 된다.
2. **투영표 보완.**
   - 부분 수행은 원본 DONE + **잔여 PLANNED 항목**이다. 잔여 항목은 분량·마감·프로젝트·배치 형식을 서비스 규칙대로 투영하고, 임시 음수 id를 쓴다.
   - 실행 생성, 완료 취소(DONE→PLANNED), 과제 생성도 표에 명시한다.
   - **공통 검증**: op마다 "가정 상태"와 "실제 적용 후 재조회 상태"가 같은지 비교하는 DB 테스트를 둔다. 임시 id는 적용 결과의 실제 id로 연결해 비교한다.
3. **자정 UI 왕복.**
   - S2·S5에 다음을 포함한다:
     - `PlanWeekPreview`가 종료 날짜를 유지한다.
     - `WeekGrid`의 표시 범위를 항목에 맞춰 넓힌다(새벽 항목이 있으면 00시부터).
     - `useProposalDraft`가 종료 날짜를 시작 날짜로 덮어쓰지 않는다.
     - 실행 이동 경로도 같은 자정 규칙을 쓴다(`validatePlacement` 정리).
   - 검증: 23~24시와 다음 날 00~01시 항목의 미리보기 → 편집 → 확정 → 재조회.
4. **휴식은 "예산상 여유분"이다.**
   - 범위만 말한 경우 목표 공부량에서 휴식 여유(연속 60분당 10분)를 뺀다.
   - 화면 문구는 "휴식 여유 N분을 남겼어요"다. 배치가 그 간격을 보장한다고 말하지 않는다.
   - 솔버의 간격은 기존 SOFT 선호 그대로 둔다.
   - 테스트: 식사로 나뉜 창, 정확히 60분인 창.
5. **자료 판정 누적.**
   - "자료를 읽었다"는 서버 판정을 도구 단계 전체에 누적한다.
   - 그 판정을 답변 단계의 기억·합의 저장 제한(기존 `restrictDraftOps`·기억 재추출)에 전달한다.
6. **문서**: §2의 잘못된 예시("8시까지는 근무 전이라 영향 없음")를 고쳤다.
