## 1. 전체 완료 기준 (같은 요청을 처음부터 다시 만들었을 때)

1. 사용자가 직접 말한 목표·범위·시험 방식이 미승인 AI 제안으로 낮아지지 않는다.
2. 과목별 시험 범위가 계획에 반영되거나, 제외·보류 이유가 드러난다.
3. 자료를 확보하지 못했다는 이유로 목표(예: 코드 완성 연습)가 범위 확인으로 바뀌지 않는다.
4. 필수 과목이 덜 준비된 채 추가 과목을 넣었다면 그 판단을 설명한다.
5. 처리하지 못한 범위가 있는데 "오늘 끝내는 계획"처럼 보이지 않는다(화면에도 미처리 범위와 이유가 보인다).

성공은 계획 시간이 늘었는지가 아니라 위 다섯 가지로 판단한다. 앱이 확인하지 못한 실제 문항·페이지·코드 내용은 만들어 내지 않는다.

## 2. 중심 구조: 생성 건별 "요청 범위 목록"

합의(planBrief)는 상담 모델의 ADD 누락에 약하다(이번 사례). 그래서 대조 기준을 합의에만 두지 않고, **계획 생성마다 사용자 원문에서 범위 목록을 먼저 확정한다.**
범위와 자료 선택을 같은 응답에서 받으면 둘이 함께 빠질 때 잡지 못하므로 호출을 나눈다.

**순서**: ① 범위 추출 호출(SCOPE) → ② 서버 검증·부분 확정·저장 → ③ 카탈로그 구성(첫 미학습 표시는 이 범위를 보고 과목별로) → ④ 자료 선택(SELECTION, 범위 목록은 입력으로만)
→ ⑤ 원문 전달 → ⑥ 계획(PLAN) → ⑦ 서버 최종 판정. ④ 이후 호출은 범위를 지우거나 id를 다시 매기지 못한다(서버가 원본을 들고 있다).

- **범위**(scope): `scopeId`(서버가 매김, 생성 건 안에서 유일), `courseId`(모르면 null), `role`(REQUIRED/OPTIONAL — "끝내고 싶어"/"가능하면"), `goal`(예 "PDF 보고 코드 빈칸 채우기"),
  `boundary`(시작·끝·제외), `quote`(사용자 원문 구절), `basisSentence`(서버가 원문에서 찾은 그 문장 전체), `verified`.
- **부분**(parts): 범위를 독립적으로 누락을 판정할 수 있는 단위로 나눈다 — "2·3·6·7주차(7주차 56장까지)"는 주차 넷, "Navigation·RecyclerView·SQLite·이벤트 처리"는 넷.
  "붓꽃·타이타닉까지"처럼 누적 범위는 ②에서 서버가 과목 자료 순서(주차·장 번호·목차)에 시작·끝·제외를 적용해 부분(자료·장 단위)으로 펼친다. 순서를 확정할 수 없으면 경계 미확인 부분 하나로 둔다.
- **검증(②)**: quote는 서버가 대화에서 직접 조회한 이번 요청의 USER 메시지(같은 사용자·같은 대화) 원문에 있어야 한다. 최신 정정·철회가 옛 원문보다 우선.
  검증 실패 범위는 `verified=false` 후보로 보존하되 **필수 예산을 받지 않고, 검증된 범위를 밀어내지 않고, 충족 근거가 되지 않는다.** 화면에는 "확인 필요"로 보인다.
- **연결 검증**: 선택 구간·전달 원문·최종 항목이 다는 `scopeId/partId`는 이 생성 건의 것이어야 하고, 과목이 범위의 과목과 같아야 하며, 구간·자료는 그 사용자 소유여야 한다.
  과목 미확정 범위는 임의 과목 연결로 "반영"이 되지 않는다.
- **상태는 부분마다 둘**: 확보 상태(원문 단위 전달 / 발췌만 / 보였으나 미선택 / 자료 있음·미확보 / 앱에 자료 없음) ·
  반영 상태(항목 반영 / 사용자 자료로 연습 반영 / 시간 부족으로 보류 / 이미 준비됨(근거 있음) / 미처리). 범위 상태 = 부분 상태의 집계(전체·부분·없음).
- **판정**: 부분의 충족 기준은 하나다 — 반영 상태가 {항목 반영, 사용자 자료로 연습 반영, 이미 준비됨(근거 있음)}이면 충족(시간 부족 보류·부분 반영·미처리는 미충족).
  집계 대상은 쓰임에 따라 나눈다.
  - **필수 미충족**(추가 과목 설명 검사용): 검증된 REQUIRED 부분 중 미충족이 있는가.
  - **남은 범위**(화면 표시용): 검증된 범위 전체(OPTIONAL 포함, "선택"이라고 표시)의 미충족 부분.
  - **확인 필요**(별도 표시): `verified=false` 범위. 충족 판정에서 빼고, 이것으로 요청 전체가 반영됐다고 하지 않는다.
  - **완료 문구**: 검증된 범위가 하나도 없으면 완료를 말하지 않는다(확인할 수 없음 ≠ 충족). 필수만 충족이면 "필수 범위 반영"으로 대상을 한정하고 남은 선택 범위·확인 필요를 함께 보인다.
    모든 검증 범위가 충족이고 확인 필요가 없을 때만 전체 반영으로 표시한다.
- 저장: 요청 맥락(plan_request_json)에 범위·부분·두 상태를 남긴다. 생성 기록에도 SCOPE 호출이 실린다.

## 3. 단계

### 1단계 — 사용자 의도 보존(합의 저장)
구분: **작성 주체**(speaker) / **근거**(서버가 확인한 사용자 메시지 id + 그 문장) / **해석**(text) / **승인**(accepted·acceptedBy). 새 표 없이 합의 항목에 근거 필드를 더한다.

- `PlanBriefOp`·상담 응답 스키마에 `quote`를 더한다. 파서 → apply → 저장(JSON) → 재조회 → history → 상담·계획 프롬프트 렌더링까지 같은 이름으로 전달.
- **근거 검증과 승인을 분리한다.** 근거 메시지는 모델이 준 id를 믿지 않고 서버가 아는 이번 턴의 요청 메시지(requestMessageId, 같은 사용자·대화·USER 역할)로만 정한다.
  - speaker=USER이고 quote가 그 메시지에 있다 → 사용자 진술(유효), 근거 = 그 메시지·문장.
  - speaker=ASSISTANT이고 quote가 있다 → AI가 사용자 발언을 해석한 항목: 작성 주체는 ASSISTANT 그대로, 근거 연결, **사용자 요청에 근거하므로 유효**하되
    프롬프트에는 "해석"과 "원문 문장"을 함께 싣고 원문이 기준이라고 둔다.
  - quote가 없거나 메시지에 없다 → speaker 값과 무관하게 **AI 제안(후보)**. 지금처럼 speaker=USER만으로 자동 승인하지 않는다.
- 중복: `speaker+text`가 같은 기존 항목이 있으면 건너뛰지 않고 근거만 붙인다(같은 scope·기간·과목일 때만). 기간·과목이 다르면 새 항목.
- UPDATE: 해석이 바뀌면 근거·승인은 그 수정판의 근거로 다시 정한다(이전 판의 근거를 무조건 승계하지 않는다, history에는 남긴다).
- REJECT·REMOVE·supersedes·기간 지남은 근거가 붙어도 되살아나지 않는다. 철회된 요구를 사용자가 다시 말하면 새 항목 + 이전 항목 id 연결.
- 기존 저장본(근거 필드 없음)은 그대로 읽히고 기존 승인·거절·삭제 상태가 바뀌지 않는다.
- 상담 프롬프트 규칙 23·25: 사용자 발언을 옮길 때 quote를 반드시 낸다.

### 2단계 — 자료 확보
- **지정 자료 식별**: 명시 id → 원래 파일명 일치 → 제한적 정규화 후보 순서. 정규화는 파생 키에만(원본 이름 불변): 확장자, 끝의 `_v숫자`, ` (숫자)`만 뗀다.
  `_WSL2추가` 같은 내용 표시는 지우지 않고 "포함 일치" 후보로만 쓴다. 과목을 먼저 제한하고 주차·장 번호는 숫자 경계로 비교(1과 10 구분).
  같은 주차에 여러 판이 남으면 최신을 추정해 확정하지 않고 "후보 여럿"으로 선택 단계에 함께 보인다.
- **펼친 묶음**: 앞부분 몇 개만이 아니라 묶음 전체의 구간 제목·쪽 범위를 한 줄씩 압축해 보인다(원문 미포함). 줄 상한을 넘으면 범위(장·쪽)별로 접는다.
- **원문 예산**: 최종 직렬화한 계획 입력(시스템+사용자)의 토큰 추정치가 상한 안에 들 때까지 조정하고, 조정이 끝난 **최종 입력 기준으로** 확보 상태를 계산한다.
  검증된 REQUIRED 부분 → OPTIONAL 순으로 부분마다 최소 몫을 먼저 배정하고 남는 몫을 나눈다.
  - 최소 몫 합이 예산을 넘으면: REQUIRED 범위부터 확보하고, 못 받은 범위는 확보 상태 "자료 있음·미확보(예산)"로 남긴다(조용히 빠지지 않는다).
  - 원문 단위(코드 블록·문제 하나)가 몫보다 크면: 기존 추가 읽기 호출(PLAN_MORE_EVIDENCE, 기존 횟수·입력 상한 그대로)에서 그 단위를 우선 다시 받는다.
    추가로 읽어도 최종 입력에 실리지 못하면 전달로 세지 않는다.
  - 최종 입력에 실린 양이 0이면 "자료 있음·미확보", 일부면 "발췌만", 단위가 완결되면 "원문 단위 전달"(구간당 글자 수가 아니라 단위 완결 여부).
- **맥락 선별**: 다른 프로젝트 한정·지난 날짜 한정 맥락은 싣지 않는다. 프로젝트 무관 전역 조건(예: "금요일 밤은 비움")은 유효 기간 안이면 보존. 같은 주제의 최신 정정·철회가 옛 원문보다 우선.
- 검증: 파일명 매칭(접미사·숫자 경계·후보 여럿), 예산 분배(최소 몫 불가·큰 단위), 맥락 선별 단위 테스트.

### 3단계 — 계획 판단
- **첫 미학습은 과목별로 제어**한다(③ 카탈로그 구성 때): 범위 목록에 그 과목의 범위가 있으면(경계 미확인 포함) 그 과목에는 "첫 미학습"을 범위 대신 넣지 않는다. 범위 안의 순서 참고로만 쓴다.
  학습 진도와 시험 범위는 별도 사실로 둔다. 기록상 미학습이 실제 지식 없음을 뜻하지 않는다.
- **"…까지"**: 시작점·제외 조건을 먼저 적용하고, 시작이 없으면 과목 자료 순서상 앞부분부터의 누적 범위로 본다. 순서를 확인할 수 없으면 경계를 미확인으로 둔다.
  앞부분 중 이미 준비된 부분은 확인된 근거(실행 기록·사용자 진술)가 있을 때만 줄이고 그 근거를 적는다.
- **자료 미확보는 목표 축소 이유가 아니다**: 원문이 없으면 사용자가 가진 자료를 가리키는 연습 항목을 만든다(예: "허용 PDF만 보고 Navigation·RecyclerView 코드 빈칸 채우기",
  "교재에 표시한 시험 범위 복습·셀프 테스트") — 실제 문항·쪽·코드는 지어내지 않고 "앱이 내용 미확인"으로 표시. "앱에 자료 없음"과 "사용자에게도 없음"을 구분(사용자 말로만 판단).
- **최종 판정(⑦, 서버)**: 범위·부분과 최종 항목을 대조해 반영 상태를 채우고 §2의 공통 미충족 판정을 계산한다.
  - 필수 미충족인데 OPTIONAL 범위의 항목이 있으면 계획 출력의 판단 이유(어느 범위를 왜 미루고 추가 과목을 넣었나)가 있어야 한다. 없으면 초안을 "검증 미통과"로 표시하고
    이유 칸에 서버가 미충족 부분과 그 상태를 적는다(경고만 남기지 않는다).
  - 완료 표시는 문구 치환이 아니라 §2 판정으로 제어한다: 남은 범위·확인 필요가 있으면 초안 상단에 서버가 만든 줄을 붙이고, 모델의 목표 문장은 "목표"로만 보인다.
- 화면(diary-ui): 계획 미리보기에 범위별 확보·반영 상태와 이유를 보인다.

### 4단계 — 통합 검증
- **고정 응답 회귀 테스트**: 상담 응답 스키마 → 파싱 → apply → 저장·재조회 → 계획 프롬프트 → 선택·전달 → 최종 초안. 포함 사례: speaker=USER인데 근거 틀림, ADD가 아예 없음,
  기존 제안에 근거만 추가, 선택 0개·전달 0개, 단일 코드 블록 예산 초과, 버전 접미사 파일, SQLite 자료 없음, 영어 목차만,
  범위와 선택의 동시 누락, 복합 범위의 일부만 연결, 시간 부족 보류와 선택 과목의 동시 존재, 근거 없는 REQUIRED 범위, 추가 읽기 후 최종 입력에서 다시 빠지는 경우,
  필수 전부 반영 + 선택 범위 보류, 범위 전부 검증 실패, 모든 범위 검증·반영 완료(세 표시가 구분되는지).
- **합성 계정 실호출**: 이번 사례와 같은 구조로 같은 요청을 처음부터 실행(실제 사용자 자료는 쓰지 않는다). 입력 → 선택·전달(생성 기록) → 최종 초안을 완료 기준 1~5로 대조.

## 4. 순서와 단위

단계마다 구현 → 테스트 → Codex 코드 리뷰 → 커밋. 1단계(합의 근거) → §2 범위 목록(SCOPE 호출·부분·판정 골격) → 2단계 → 3단계 → 4단계 순서. 배치 알고리즘은 바꾸지 않는다.
