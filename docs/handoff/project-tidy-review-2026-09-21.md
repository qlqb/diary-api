## 1. 환경 격리 — 가장 먼저 한 일

**발견**: 사용자의 IntelliJ 개발 서버(pid 33120, 8080, 2026-09-20 시작)는 클래스패스에
`diary-api\build\classes\java\main`을 두고 devtools로 지켜본다. 메인 체크아웃에서 gradle을 돌리는 순간
그 서버가 **내 새 클래스로 재시작**해 사용자 DB(`memo`)에서 worker를 돌린다. 직전 작업의 합성 표본 유입이
이 경로였다. 테스트의 worker만 끄는 것으로는 막을 수 없다.

**조치**
- API 작업을 별도 워크트리로 옮겼다 — 빌드 산출물이 다른 폴더라 devtools가 보지 않는다.
- DB 테스트를 `memo_test`로 갈랐다(`build.gradle` systemProperty). `scripts/test-db/prepare-memo-test.sh`가
  `memo`에서 **스키마만**(`--no-data`) 떠 오고, 이 브랜치의 새 마이그레이션을 테스트 DB에만 얹고, 합성 사용자
  하나를 넣는다. `TestDatabaseIsolationTest`가 매 실행마다 "memo가 아니다"와 "테이블이 갖춰져 있다"를 확인한다.
- 업로드 경로도 `build/test-materials`로.
- 사용자 프로세스는 건드리지 않았다(검증용 서버는 8081·5174에 따로 띄웠다).

**격리하자 드러난 것**
- `memo`에 합성 사용자(999xxxxxx)의 분석 작업 행 **172건**이 지난 실행들에서 남아 있다(9-13 ~ 9-21).
  `ProjectTidyApplyDbTest` 한 건은 이 남은 행 덕분에 통과하고 있었다 — 테스트가 제 전제를 직접 만들도록 고쳤다.
  **남은 172건은 지우지 않았다**(사용자 DB의 삭제는 이 작업 범위 밖). 지우려면:
  `DELETE FROM memo.material_analysis_jobs WHERE user_id >= 999000000;` (먼저 백업)
- 계획·교재 쪽 DB 테스트 **아홉 개가 "users 표의 첫 번째 사용자"를 빌려 쓴다.** `memo`에서 그것은 실제 계정
  `user_id=1`이다. 이 테스트들은 그동안 실제 계정 이름으로 행을 쓰고 지웠다. `memo_test`에는 합성 사용자만 있다.
  (이 테스트들의 설계는 이번 범위 밖이라 그대로 두었다.)

**사용자 DB 비변경 확인**(작업 시작 때와 끝, 13개 관련 표 행 수 비교): 전부 같다. `memo` 스키마에 새 열 0,
오늘 생긴 사용자 0. 새 마이그레이션은 `memo`에 **적용하지 않았다**.

## 4. 실제 모델 검증(격리 서버 8081 → memo_test, 합성 자료만)

스크립트 `scripts/ai-baseline/verify-project-tidy-review-2026-09-21.py`. 두 번 돌렸다.

**1회차(예산 2,500/4,000자)**: 합성 자료가 작아 자료마다 구간 1개 → 전부 상세 예산에 들어가 **고르기 호출이
일어나지 않았다**(호출 1). 이 회차로는 고르기 경로를 확인하지 못했다. 마지막 자료는 기존 「스택 기본 동작」에
LINK됐다(중복 항목 없음). 압축 흐름은 끝까지 됐다.

**2회차(상세 예산 700자로 낮춰 고르기를 강제)**:
- 자료 7개 · 구간 9개 **모두 목록 수준** · 상세 4개 · **모델 호출 2**(고르기 1 + 판단 1) · 부분 정리 아님.
- 고르기 호출이 **맨 마지막에 올린 자료의 구간 3개를 전부** 상세로 골랐다(입력 순서가 아니라 관련도로).
- 그 자료는 기존 「스택」 **아래 하위 항목** 셋으로 붙었다(새 최상위 「스택」을 만들지 않았다). LINK가 아니라
  하위 ADD를 택했다 — 판단으로서 타당하지만, 스크립트의 "기존 스택에 LINK" 판정은 거짓으로 나왔다.
- 목록 줄만 본 채움 자료 다섯은 제목으로 최상위 항목이 됐다.
- 관찰된 품질 문제: 1단계에서 이미 연결된 구간에 대한 LINK를 다시 제안했다(되풀이 3건, 적용해도 변화 없음).
  이번 범위에서 고치지 않았다(§6).
- 압축: 업로드 직후(READY 전) 압축 묶음 없음 → 확정 → 묶음 1개(자리 2, "과제모음.zip") → 경로
  "과제1/run.sh"·"과제2/run.sh"로 구분 → 12초 뒤 FINISHED(성공 2) → 정리 준비 자료 수에 포함(9).

모킹 검증과의 구분: 경합·스냅샷·승계·묶음·근거의 판정은 DB 테스트(실제 SQL·실제 트랜잭션, 모델만 가짜)가 했다.
실제 모델로 확인한 것은 위 목록뿐이다. 입력이 목록 예산마저 넘쳐 **조각을 여러 개로 나누는 경로와 고르기 한도
초과(부분 정리)는 실제 모델로 돌려 보지 않았다** — 단위 테스트로만 봤다.

## 5. 브라우저 확인(1536×760)

검증용 화면 서버 5174(→ API 8081, memo_test)를 띄우고 합성 계정과 정리안을 준비했다. 로그인은 사용자가 직접 한다

## 6. 남은 한계

- 이미 연결된 구간의 LINK를 다시 제안하는 것(§4). 적용은 변화가 없지만 정리안이 불어난다.
- 조각을 나누는 고르기 경로·한도 초과는 실제 모델로 확인하지 않았다(단위 테스트만).
- 새 편집 저장소(localStorage 복구)는 같은 브라우저 안에서만 복구한다. 다른 기기에서는 서버에 닿은 편집만 보인다.
- 올리다 만 자리를 거두는 30분은 고정값이다. 매우 느린 망에서 20MB 파일 여러 개를 순서대로 올리면 뒤쪽 자리가
  먼저 거둬질 수 있다(그 파일은 다시 골라 올려야 한다).
- 새 마이그레이션은 `memo`에 적용하지 않았다. 이 브랜치를 사용자 DB에서 띄우려면 먼저 적용해야 한다(§7).
- `memo`에 남은 합성 작업 행 172건(§1)과, 실제 계정을 빌려 쓰는 계획·교재 DB 테스트 아홉 개.
