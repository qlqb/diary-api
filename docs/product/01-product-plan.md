# 01. Product Plan

> 현재 기준: 2026-08-03. 과거 v2.1 문서와 충돌하면 이 문서와 `99-changelog.md`를 우선합니다.

## 1. 한 줄 정의

diary-app은 GPT와 만든 생각과 계획을 편집 가능한 화면으로 보여주고, 사용자가 확정한 내용을 오래 기억하며, 오늘 실행과 다음 계획에 연결하는 개인 운영 웹 애플리케이션이다.

## 2. 해결하려는 문제

사용자는 GPT와 대화하면서 목표, 고민, 현실적인 제약, 계획을 정리한다. 그러나 결과가 채팅 문장으로만 남으면 세 가지 문제가 생긴다.

1. 좋은 결론과 계획이 대화 속에 묻혀 다시 찾기 어렵다.
2. 기존 Todo와 캘린더는 사용자가 이미 무엇을 해야 하는지 안다고 가정한다.
3. 계획이 무너졌을 때 완료/미완료만 남고, 왜 이동·축소·보류했는지는 다음 계획에 반영되지 않는다.

diary-app은 대화 내용을 곧바로 Todo로 저장하지 않는다. 먼저 목표·결정·제약·계획 후보로 구조화하고, 사용자가 고치고 승인한 것만 공식 데이터로 만든다.

## 3. 핵심 사용자 경험

```text
상황을 자연어로 설명한다
→ AI가 목표·결정·제약·계획 후보를 만든다
→ 계획 초안과 실행 조각이 화면에 미리 보인다
→ 날짜·시간·제목·순서·분량을 직접 또는 대화로 수정한다
→ 필요한 항목만 선택해 적용한다
→ 오늘과 실행 화면이 갱신된다
→ 완료·부분 수행·미수행과 조정 사건을 기록한다
→ 확인된 맥락과 실제 결과가 다음 상담에 사용된다
```

화면이 대화 중 실시간으로 바뀌는 경험은 유지한다. 단, 대화 중 변화는 `미리보기/차이 표시`이며, 사용자가 적용하기 전에는 공식 계획과 실행 데이터를 덮어쓰지 않는다.

## 4. 제품의 중심 구조

최상위 탭은 다음 네 개다.

| 영역 | 사용자가 답하려는 질문 | 주 데이터 |
| --- | --- | --- |
| 오늘 | 지금 무엇을 하고, 남은 오늘을 어떻게 조정하지? | 오늘 날짜의 `ExecutionItem`, `DailyState` |
| 계획 | 앞으로 무엇을 어떤 기간과 순서로 진행하지? | `PlanItem`, 계획 초안, 관련 `ContextItem` |
| 실행 | 여러 날짜와 시간에 어떻게 배치하고 운영하지? | 기간 내 `ExecutionItem`과 시간표 |
| 기록 | 실제로 무엇이 일어났고 왜 달라졌지? | `ExecutionRecord`, `ExecutionItemEvent` |

AI 상담 패널은 별도 최상위 탭이 아니라 네 영역을 연결하는 전역 보조 도구다. Quick은 빠른 기록·조각 추가·상담을 여는 축약 진입점이다.

## 5. 제품 정체성

이 앱은 다음 중 하나로 축소되지 않는다.

- 단순 Todo 앱
- 자동 시간 배치 캘린더
- 일기 또는 감정 기록 앱
- 대학생 전용 학습 플래너
- AI 답변을 저장하는 채팅 보관함

대학생의 과목·강의계획서·학기·방학 계획은 첫 번째 주요 사용 사례다. 핵심 구조는 취업 준비, 생활 운영, 개인 프로젝트, 건강 루틴처럼 다른 영역에도 동일하게 적용돼야 한다.

## 6. 핵심 데이터 원칙

```text
PlanItem               무엇을 하려는가
ExecutionItem          실제로 관리 가능한 실행 조각
ExecutionRecord        실제로 무엇을 했는가
ExecutionItemEvent     계획을 어떻게 조정했는가
ContextItem            다음 결정에 다시 쓸 기억
AIProposal             아직 적용되지 않은 AI 초안
```

같은 실행 항목을 오늘·계획·실행·기록 화면이 각각 따로 저장하지 않는다. 하나의 원본을 화면 목적에 맞게 조회한다.

## 7. AI 원칙

- AI는 DB를 직접 수정하지 않는다.
- AI 결과는 문장만이 아니라 계획 카드, 실행 조각, 시간표 블록, 컨텍스트 후보로 변환한다.
- 사용자는 화면에서 직접 수정하거나 대화로 다시 조정할 수 있다.
- 제안은 `제안 → 검토 → 수정 → 적용` 단계를 거친다.
- 거절·수정 후 적용·만료도 다음 제안 품질을 위한 반응 데이터로 남긴다.
- AI가 추정한 장기 컨텍스트는 사용자 확정 전까지 사실로 취급하지 않는다.
- 오래된 제안은 대상 데이터의 버전이 달라졌다면 적용하지 않고 다시 생성하게 한다.

## 8. 장기 컨텍스트 원칙

다음과 같은 정보는 일회성 채팅 문장이 아니라 재사용 가능한 컨텍스트 후보가 될 수 있다.

```text
평일 저녁에는 알바가 있다.
알바 다음 날은 가벼운 계획이 낫다.
공부 자료는 정해진 순서대로 진행한다.
한 번에 긴 계획을 잡으면 자주 미룬다.
```

각 컨텍스트는 출처, 확인 상태, 현재 유효 여부를 가진다. 새 정보가 과거 정보와 충돌하면 조용히 덮어쓰지 않고 교체·보관 관계를 남긴다.

## 9. 차별점

### 9.1 대화에서 실행까지 연결

일반 챗봇은 계획을 말로 끝내고, 일반 Todo는 사용자가 항목을 직접 정의해야 한다. diary-app은 아직 정리되지 않은 자연어를 편집 가능한 계획과 실행 데이터로 번역한다.

### 9.2 실패가 아니라 조정 데이터를 남김

이동, 축소, 보류, 분할은 단순 수정이 아니라 다음 계획을 현실적으로 만드는 근거다.

### 9.3 계획과 실제를 분리

예정된 `ExecutionItem`과 실제 수행인 `ExecutionRecord`를 분리한다. 부분 수행은 원래 항목을 애매하게 완료 처리하지 않고, 실제 기록과 남은 조각을 함께 만든다.

### 9.4 개인 컨텍스트를 재사용

확인된 목표·결정·제약·선호를 다음 상담과 계획 생성에 다시 사용한다. 단순 채팅 기록 검색보다 명시적이고 수정 가능하다.

## 10. 첫 번째 검증 기준

첫 사용자는 개발자 본인이다. 30일 자가사용은 여전히 필요하지만, 단순 연속 접속만으로 성공을 판단하지 않는다.

확인할 항목은 다음과 같다.

- 상담 결과를 실제 계획으로 적용하는 흐름이 반복해서 사용되는가
- AI 초안을 화면에서 직접 고칠 수 있는가
- 오늘 실행 조각이 부담스러운 크기일 때 이동·축소·보류가 자연스러운가
- 부분 수행과 미수행 이유가 다음 계획에 반영되는가
- 저장된 컨텍스트가 다음 상담에서 실제로 도움이 되는가
- Today 목록과 주간 시간표의 동일 항목이 일관되게 바뀌는가

## 11. 기술 기준

```text
Frontend: React + Vite + Tailwind CSS
Backend: Spring Boot + MyBatis Mapper/XML
Database: MySQL 또는 MariaDB
Authentication: Spring Security + JWT
```

현재 구현을 존중하되 JPA 전환이나 별도 대규모 인프라를 전제로 하지 않는다.
