# 01. 제품 개요

> 현재 기준: 2026-10-25(전면 개정. 2026-08-03판은 git 이력에 있다). 무엇을 만드는지의 **가설**은 [12-product-thesis.md](12-product-thesis.md),
> 핵심 경험과 컨텍스트 경계는 [10-core-experience.md](10-core-experience.md)가 기준이다. 이 문서는 지금의 제품 모양을 한 장으로 요약한다.

## 1. 한 줄 정의

자료·상담·실행 기록으로 사용자의 현실(시간·진도·막힘·시험 범위)을 모으고, 그 위에서 기간 학습 계획 초안을 만들며, 사용자가 확인한 것만
오늘의 실행과 기록으로 이어 가는 개인 운영 웹 애플리케이션이다. 실행 결과는 다시 현실로 돌아가 다음 계획을 바꾼다(12번 4층 구조).

## 2. 해결하려는 문제

1. 좋은 결론과 계획이 대화 속에 묻혀 다시 찾기 어렵다.
2. Todo·캘린더는 사용자가 무엇을, 얼마나 해야 하는지 이미 안다고 가정한다. 실제로는 자료·시험 범위·남은 시간을 매번 다시 계산해야 한다.
3. 계획이 무너졌을 때 완료/미완료만 남고, 왜 이동·축소·보류했는지는 다음 계획에 반영되지 않는다.
4. AI가 대화를 정리하는 과정에서 사용자가 직접 말한 범위·시간이 낮아지거나 빠진다(21번).

## 3. 핵심 사용자 경험

```text
자료를 올린다(자동 분석·자료 구간·교재 목차)  ·  상담에서 상황을 말한다(사진 포함)
→ 앱이 진도·시험 범위·막힘·해결을 기억한다(학습 기억·학습 이벤트)
→ 계획을 요청하면 요청 범위·말한 시간을 원문과 대조해 확정하고, 자료 원문을 골라 기간 계획 초안을 만든다
→ 초안 미리보기에서 "말한 범위"가 어떻게 담겼는지 서버 판정으로 보고, 고치거나 다시 만든다
→ 확정하면 실행 조각이 오늘·일정에 배치된다
→ 완료·부분 수행과 이동·축소·보류가 기록된다
→ 다음 상담과 계획이 그 기록을 쓴다
```

AI의 제안은 사용자가 확정·적용하기 전까지 계획·일정 같은 공식 데이터를 바꾸지 않는다. 상담에서 말한 사실의 **기억**은 승인 팝업 없이 저장되지만
(CONSULT_AUTO) 서버가 원문과 대조하고, 사용자가 고치거나 지울 수 있으며, 사실 카드에 출처와 함께 보인다(10번 §4.2, 18번).

## 4. 화면 구조

최상위 탭은 여섯 개다(diary-ui `src/shell/MainShell.jsx`). 관리 단위는 **프로젝트**(과목·개인 개발·자격 준비)다.

| 탭 | 사용자가 답하려는 질문 | 주 데이터 |
| --- | --- | --- |
| 오늘 | 지금 무엇을 하고, 남은 오늘을 어떻게 조정하지? | 오늘 날짜의 `execution_items`, 과제 마감, 수업 확인(`class_sessions`) |
| 자료 | 무엇을 올렸고 분석은 어디까지 됐지? | `materials`, 자동 분석 작업·자료 구간 |
| 프로젝트 | 이 프로젝트에서 무엇을 배우고 어디까지 왔지? | `courses`·`course_topics`(교재 목차), `user_contexts`(기억하는 것), 정리안 |
| 계획 | 앞으로 무엇을 어떤 기간·순서로 하지? | `plan_versions`(초안·확정·회고), `scopeReport` |
| 일정 | 여러 날짜와 시간에 어떻게 배치하지? | 기간 내 `execution_items`, `routines`, `one_off_commitments` |
| 기록 | 실제로 무엇이 일어났고 왜 달라졌지? | `execution_records`, `execution_item_events` (일기 API는 서버에 있지만 메인 화면에는 없다) |

AI 상담 패널은 탭이 아니라 어느 탭에서나 여는 전역 도구다.

## 5. 제품 정체성

다음 중 하나로 축소되지 않는다: 단순 Todo 앱, 자동 시간 배치 캘린더, 일기 앱, AI 답변 보관함.
대학생의 과목·학기 운영이 첫 번째 사용 사례이고, 같은 흐름을 프로젝트 단위로 개인 개발·자격 준비에도 쓴다. 확장 순서는 12번 "확장 순서".

## 6. 핵심 데이터

```text
Project(courses)        관리 단위. 자료·목차·기억·계획이 여기에 묶인다
PlanVersion             기간 계획 한 판. 항목은 스냅샷으로 보관한다(11번)
ExecutionItem           실제로 배치·조정하는 실행 조각. 실행의 유일한 원본(03번)
ExecutionRecord         실제로 무엇을 했는가
ExecutionItemEvent      계획을 어떻게 조정했는가
UserContext             상담에서 기억한 사실(18번)
PlanBrief               상담 합의 — 작성 주체·근거·승인(13번 §11, 21번)
LearningEvent           원천을 가리키는 학습 이벤트(20번)
AiProposal              아직 적용되지 않은 AI 제안
```

같은 실행 항목을 오늘·일정·기록 화면이 따로 저장하지 않는다. 하나의 원본을 화면 목적에 맞게 조회한다. 테이블은 05번.

## 7. AI 원칙

- AI는 DB를 직접 수정하지 않는다. 모델은 구조화된 출력을 내고, 서버가 검증해 적용한다.
- 판단은 AI에게, 적용은 사용자에게(10번 §5.1). 제안은 `제안 → 검토 → 수정 → 적용`을 거친다.
- 사용자 원문이 AI 정리보다 우선한다. 말한 범위·시간은 서버가 원문과 대조하고, 근거가 없는 정리는 후보로만 다룬다(21번).
- 산수는 언어모델에 맡기지 않는다. 가용시간·예산·배치는 서버 계산이다(12번 판단층).
- 오래된 제안은 대상 데이터의 버전이 바뀌었으면 적용하지 않고 다시 만들게 한다(baseVersion 409).
- 거절·수정 후 적용·만료도 반응 데이터로 남긴다.

## 8. 차별점

- **대화·자료에서 실행까지**: 정리되지 않은 자연어와 자료를 편집 가능한 계획과 실행 데이터로 번역한다.
- **실패가 아니라 조정 데이터**: 이동·축소·보류·분할은 다음 계획을 현실적으로 만드는 근거다.
- **계획과 실제의 분리**: 예정(`ExecutionItem`)과 수행(`ExecutionRecord`)을 나누고, 부분 수행은 기록과 남은 조각을 함께 만든다.
- **확인 가능한 기억**: 진도·막힘·시험 범위를 출처와 함께 기억하고, 새 대화가 다시 묻지 않는다.

## 9. 검증 기준

첫 사용자는 개발자 본인이다. 연속 접속이 아니라 다음으로 본다. 관찰 질문은 12번 "일주일 실사용 관찰 질문".

- 상담·자료에서 만든 계획이 실제로 확정·실행되는가
- 말한 범위·시간이 계획에 그대로 반영되거나, 못 담은 이유가 보이는가(21번 완료 기준)
- 이동·축소·보류·부분 수행이 다음 계획에 반영되는가
- 기억한 사실이 다음 상담에서 실제로 도움이 되는가

## 10. 기술 기준

```text
Frontend: React + Vite + Tailwind CSS
Backend: Spring Boot + MyBatis Mapper/XML, Timefold(배치), Spring AI(OpenAI)
Database: MySQL 또는 MariaDB (마이그레이션은 docs/sql/ 수동 적용, Flyway 없음)
Authentication: Spring Security + JWT
```

JPA 전환이나 Kafka·Redis 같은 별도 대규모 인프라를 전제로 하지 않는다.
