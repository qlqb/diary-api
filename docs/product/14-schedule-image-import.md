# 14. 이미지에서 일정 가져오기 (Schedule Image Import)

근무표 사진을 채팅에 붙이면 일정 후보가 된다. 새 테이블도, 새 상태 기계도, 이미지 저장도
없다 — 기존 `ai_schedule_suggestions`에 COMMITMENT 후보로 들어가고 사용자가 한꺼번에
`one_off_commitments`로 적용한다.

## 1. 원칙

1. **LLM은 받아쓰기만 한다.** 셀은 원문 그대로다(`OP`, `17~23`, `D/O`). 시간 변환·날짜
   계산은 전부 서버 코드다. 모델이 `17:00`을 내면 그것이 표에서 읽은 것인지 지어낸 것인지
   서버가 구분할 수 없다.
2. **범례에 없는 코드는 창작하지 않는다.** `UNRESOLVED`로 두고 사용자에게 묻는다.
3. **LLM 호출은 트랜잭션 밖.** `extract`는 DB 쓰기 0건이다.
4. **본인 행은 서버가 고르거나(이름 일치) 사용자가 고른다.** 모델이 고르지 않는다.
5. `proposed_payload`는 `CommitmentCreateRequest`와 같은 모양이다.
6. `D/O`는 후보를 만들지 않는다. 빈 시간이 곧 휴무다.
7. 1차는 `COMMITMENT`만. `ROUTINE`은 2차.

## 2. 확률적 검증과 결정적 검증을 나눈다

Vision 호출은 매번 다를 수 있다. 그래서 검증을 두 층으로 나눈다.

- **결정적 층** — `CellParser`, `ScheduleTableInterpreter`는 순수 함수다. 픽스처로 고정
  검증하고, 회귀는 여기서 잡는다.
- **확률적 층** — 실제 모델 호출은 `ScheduleImageVisionProbe`가 같은 이미지를 3회 보내
  관측한다. 단정문이 없다. 여기서 재실행 3회만 믿으면 테스트가 아니라 운세가 된다.

프로브는 `SCHEDULE_IMPORT_PROBE=1`일 때만 돈다. 확률적인 외부 호출이 기본 스위트에 있으면
무관한 변경이 빨갛게 뜨고(오늘 3/3이어도 언젠가 이름 한 글자가 흔들린다), 이 저장소는
공개라 API 키 없이 클론한 사람에게는 그냥 실패로 보인다. 호출 비용은 그다음 이유다.

```bash
SCHEDULE_IMPORT_PROBE=1 SCHEDULE_IMPORT_IMAGE=/path/to/dir ./gradlew test --tests '*Probe*' --info
```

이미지는 저장소에 넣지 않는다 — 동료 실명과 근무 시간이 찍혀 있다. `.gitignore`가
`src/test/resources/schedule-import/`를 막고, `SCHEDULE_IMPORT_IMAGE`로 저장소 밖을
가리킬 수도 있다.

합격 판정은 **해석기의 최종 결과**로 한다. 원문만 보면 통과 여부를 알 수 없다 — 실제로
원문 3회가 모두 멀쩡해 보이는데 후보는 0건인 상태가 있었다(§3).

## 3. §10-4 측정 기록

같은 근무표 이미지(9명 × 7일, 범례 `OP`/`CL`, 기간 9.7~13), gpt-5-mini.

### 1차 (2026-09-07) — 미통과

받아쓰기 자체는 흔들리지 않았다. 셀 63개가 3회 모두 일치했고 `year=null`, `OP`/`CL`
미치환, `D/O` 미변환, `17~23` 미정규화까지 모두 지켜졌다.

`scheduleColumns`(당시 이름 `columns`)가 흔들렸다.

| | 머리글 | 셀 | 해석 결과 |
|---|---|---|---|
| RUN 1 | 9개 `["이름","세부","월"…"일"]` | 7개 | `rowInvalid=9/9` — 후보 0건 |
| RUN 2 | 9개 (동일) | 7개 | `rowInvalid=9/9` — 후보 0건 |
| RUN 3 | 7개 `["월"…"일"]` | 7개 | `rowInvalid=0/9` |

**3회 중 2회 아무것도 만들어지지 않았다.** 원인은 모델이 아니라 계약이다. 표의 머리글
줄에는 "이름"·"세부" 칸이 정말로 있고, 당시 지시는 "표의 열 머리글을 그대로"였다. 모델은
지시를 지켰다.

### 조치

1. `ScheduleTableInterpreter`가 머리글에서 **일정 열만 골라낸다**. 요일 단독(월/Mon/
   화요일/(수)/Sat.)과 날짜 표기(9/7, 09-07, 9.7, 7일, 7(월), 9/7(월))를 인정한다. 맨 숫자
   하나는 인정하지 않는다 — 근무일수 합계 열이 그렇게 생겼다.
   - **위치를 가정하지 않는다.** 합계 열이 가운데 끼는 표가 있다.
   - **순서 보존·중복 허용.** 2주짜리 표는 "월"이 두 번 나오는 게 정상이고, set으로 중복을
     지우면 개수가 안 맞아 도로 무효가 된다.
   - **골라낸 수가 셀 수와 정확히 같을 때만 채택한다.** 안 맞으면 종전대로
     `columnsUnrecognized`. 맞을 때까지 자르면 어긋난 것을 어긋난 채로 밀어 넣는 것이다.
   - 기준 셀 수는 **최빈값**이다. 깨진 행 하나가 표 전체의 열 배치를 정하면 안 된다.
2. `columns` → `scheduleColumns`로 이름을 바꾸고, `rows[].cells`와 1:1 대응하는 열만
   담는다고 프롬프트에 명시. 이름이 계약을 말하지 않으면 주석은 읽히지 않는다.
3. RUN 1(9열)·RUN 3(7열)의 실제 원문을 픽스처로 고정
   (`src/test/resources/schedule-import-raw/`). 사람 이름만 별칭으로 바꿨다 — 이 저장소는
   공개이고, 이 버그는 이름과 무관하게 개수에서 생긴다.

### 2차 (2026-09-07) — 통과

| 기준 | 결과 |
|---|---|
| `rowInvalid=0` | ✅ 3/3 |
| `columnsUnrecognized=false` | ✅ 3/3 |
| 본인 행 5 WORK + 2 OFF | ✅ 3/3 (`17:00-23:00`, `18:00-23:00`, `18:00-23:00`, `17:00-22:00`, `18:00-23:00`, OFF, OFF) |
| period·legend·셀 원문 동일 | ✅ 3/3 (`9/7~9/13`, `OP=14~23`, `CL=15~00`, 셀 63/63) |

**`columnsNormalized` 발동률: 0/3.** 모델이 3회 모두 `scheduleColumns`를 7개로 냈다. raw
계약 개선이 실제로 먹혔다는 뜻이고, 보정은 안전망으로만 남았다.

다만 3회로 계약이 안정됐다고 말할 수는 없다. 보정 로직이 살아 있는지는 라이브 호출이 아니라
픽스처가 지킨다. 앞으로 이 값이 자주 참이면 프롬프트가 다시 어긋났다는 신호다.

### 아직 검증하지 못한 것

- **`UNRESOLVED` 실제 사례.** 이 이미지에서는 범례에 없는 코드가 나오지 않아 규칙이 발동조차
  하지 않았다. 기준을 검증한 게 아니라 발동을 안 시킨 것이다. 모호·훼손 이미지로 따로 본다.
- **읽지 못한 셀을 원문 그대로 두는지.** 같은 이유로 미검증.
- 관측된 흔들림 하나: 한 사람의 이름이 3회 중 1회 한 글자 다르게 읽혔다(동음에 가까운
  글자). 본인 행은 사용자가 확정하므로 후보에는 영향이 없지만, 이름 자동 매칭이 늘 맞지는
  않는다는 근거다. 실제 이름은 여기 적지 않는다 — 이 저장소는 공개다.

## 4. 화면

```
채팅 입력창 [+] 또는 클립보드 붙여넣기
  -> POST .../schedule-image/extract          (읽기, 저장 0건)
  -> 검토 다이얼로그 (어느 줄 · 어느 주 · 모르는 코드)
  -> POST .../schedule-image/confirm          (후보 생성)
  -> 기존 일정 후보 카드 + [모두 적용]
  -> POST /api/ai/schedule-suggestions/apply-batch
```

- **붙여넣기가 주 경로다.** 캡처 도구로 잘라 바로 붙여넣는 것이 근무표를 가져오는 가장 흔한
  방법이고, 파일로 저장한 뒤 다시 고르게 하면 그 사이에 사진이 디스크에 남는다.
- **화면이 시간을 계산하지 않는다.** 미리보기 시각은 서버가 준 `cells[].start/end`를 그대로
  쓰고, `confirm`에는 표 원문만 실린다. 화면이 계산하면 서버의 계산과 두 벌이 되고 달력에
  들어가는 값이 어느 쪽인지 모르게 된다.
- **새 카드 컴포넌트를 만들지 않는다.** `[모두 적용]`은 기존 후보 목록 위에 한 줄로 얹는다.
  새 카드를 만들면 같은 후보를 두 곳에서 그리게 된다.
- **전체 줄 목록을 늘 보여준다.** 서버가 이름으로 한 줄을 미리 고르지만 그것은 선택일 뿐이다.
  근무표의 실명과 로그인 표시명은 다를 수 있고, 잘못 고르면 남의 근무가 내 달력에 들어온다.
- 모르는 코드는 **고른 줄에 있는 것만** 묻는다.
- 오버레이 클릭으로 닫지 않는다. 코드 시간을 입력하다 바깥을 잘못 누르면 십수 초 걸린
  이미지 읽기가 통째로 날아간다.
- 문구에 실패·부족 계열 표현을 쓰지 않는다. 요일이 어긋나거나 날짜가 없는 것은 사용자가
  한 번 봐야 할 일이지 잘못된 상태가 아니다. 테스트가 이 문구 규칙을 지킨다.

## 5. 지연

Vision 호출 1회에 9.5~16.3초(3회 관측, n=3). 사용자가 기다리는 시간이므로 화면은 진행
상태를 보여야 한다.

## 6. 2차로 미룬 것

`ROUTINE` 분기, 재분석을 위한 이미지 저장, 기존 일정·루틴과의 겹침 경고, PDF 첨부.
