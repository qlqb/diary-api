# 07. 아이디어 주차장 (Ideas Parking Lot)

> 이 문서는 **결정이 아니라 기억**이다. 여기 적힌 것은 약속이 아니며, 갱신 의무도 없다.
> 규칙: append-only. 떠오르면 한 줄이라도 적는다. 정리는 주간 회고 때 한다.
> 기획서(01~06)로 승격되기 전까지 모든 미확정 아이디어는 여기 산다.
> 상태 표기: `검토 전` / `n차 이후 검토` / `보류` / `기각(사유)` / `승격(문서명)`

## 지출계획 AI 추천 (2026-07-05, 대화)

- 입력 방식은 **상담형이 아니라 기록형**. 근거: 사람은 자기 지출을 부정확하게 기억함(실제보다 30~40% 과소 보고). 상담형은 부정확한 기억이 입력이라 추천 퀄리티 상한이 낮음.
- 콜드 스타트는 온보딩 고정 질문 3~4개로 해결: 월 수입(대략) / 고정비 / 이번 달 큰 지출 예정. 1차 계획 골격은 AI 없이 규칙 기반으로 충분.
- 흐름: 온보딩(1회) → 지출 퀵로그 누적(15초 예산) → 월말 "지출계획 후보 받기"(사용자 트리거) → AI 후보 → 확인 → 수정 → 적용 → 실적이 다음 달 후보에 반영(15장 피드백 루프).
- 기존 설계에 새 개념 불필요: `ai_suggestions.suggestion_type = SPENDING_PLAN` 추가 수준.
- 토큰 비용 전략: **서버가 집계하고 AI는 해석만**. 원본 거래내역을 프롬프트에 넣지 않음(비싸고, 산수 틀리고, 개인정보 원칙 위반). 요청당 2~3천 토큰 수준 → 1인당 월 비용 원 단위. 안전장치 4종: 사용자 트리거 전용 / 결과 캐싱(ai_suggestions.content 저장, 같은 달 재요청 시 저장본) / 모델 티어링(집계 해석은 경량 모델) / 월 주기 기능이라 설계 자체가 rate limit.
- "토큰을 더 사서 감당"은 답이 아님. 비용은 설계 단계에서 해결. 비용이 문제 될 규모 = 수익화 시점.
- 상담형 채팅은 도입하더라도 "후보를 받은 뒤 조정하는 대화"로 축소. 장기.
- 상태: **3차(지출 기록) 이후 검토**

## 틈새 타깃 후보 (2026-07-05, 시장 분석 대화)

- 정면승부 금지: 가계부=토스/뱅크샐러드, AI 스케줄링=Motion/Reclaim, 올인원=히로/Notion, AI 일기=40+개. "생산성 앱 시장"이 아니라 틈새로 진입.
- 쐐기 후보 1: **한국 수험생/대학생 갓생 문화** — 열품타 계보. "무너져도 다시 잡는 앱" 메시지가 번아웃 담론과 부합.
- 쐐기 후보 2: **ADHD/실행기능 어려움 커뮤니티** — Motion조차 ADHD를 추천 대상으로 명시할 만큼 수요 검증됨. 이 앱의 설계(재배치 버튼, 자기비난 방지 언어, 초저마찰 입력, LIGHT 강도)가 우연히 이 집단에 정확히 부합.
- 공개 경로: 본인 30일 → 주변 5~10명(대학생) → 반응 시 틈새 커뮤니티 공개. 각 단계가 다음의 전제.
- 상태: **보류 (본인 30일 검증 통과 전에는 착수 금지)**

## 차별점 보호 원칙 (2026-07-05, 시장 분석 대화)

- 시장 경쟁 앱들의 공통 전제 = "더 생산적이 되고 싶다"(최적화). 이 앱의 전제 = "계획은 무너지고, 그건 실패가 아니다"(조정/회복). 같은 시장의 다른 앱이 아니라 다른 질문.
- 경쟁 앱이 안 하는 것 3개 = 이 앱의 존재 이유:
  1. **조정 이력의 1급 데이터화** (plan_item_events — 밀린 일이 빨간 뱃지가 아니라 분석 원천)
  2. **컨디션이 계획에 선행** (intensity + conditionTags)
  3. **도메인 교차** (수면 × 감정 × 이월 × 지출 — 한 그릇에 담긴 앱만 가능)
- 원칙: 구현 우선순위에서 이 3개는 절대 밀리지 않는다. 기능 추가 제안이 오면 "3개 중 무엇을 강화하는가"로 심사.
- 리스크 인지: 차별점이 전부 "써봐야 느껴지는" 종류라 스크린샷 마케팅이 어렵고 복사 가능. 해자는 기능이 아니라 축적된 개인 데이터와 루프.
- 상태: **원칙으로 상시 적용**

## Pending 알림 정책 / 설정 (2026-07-08, 대화)

- pending은 이전 운영일의 미정리 ScheduleBlock이며, 실패가 아니라 정리 대상이다.
- 기본 방향은 다음 날 아침 pending 요약 알림이다.
- 사용자를 즉시 압박하지 않는 것이 기본값이다.
- 선택 설정으로 TIME_FIXED 블록의 end_time이 지난 뒤 즉시 알림을 제공할 수 있다.
- 즉시 알림은 TASK에는 적용하지 않는다. TASK는 start_time/end_time이 없기 때문이다.
- 설정 후보:
  - 알림 끄기
  - 다음 날 아침 요약
  - 시간이 지난 TIME_FIXED 즉시 알림
  - 둘 다
- 세부 설정 후보:
  - morningReminderTime
  - immediateReminderDelayMinutes
  - quietHours
- 실제 PWA notification / push notification 구현은 MVP 제외이며, 1차-D 이후 또는 별도 릴리스에서 검토한다.
- 상태: **1차-D 이후 검토**

## 완료/완료취소 반복 호출 장기 보안 전략 (2026-07-09, 보류)

- Bucket4j 또는 Filter/Interceptor 기반 사용자별 요청 제한은 1차 MVP 이후 검토한다.

- 상태: **1차 MVP 이후 / 외부 사용자 공개 전 검토**

## ScheduleBlock scale-up / rescale 장기 검토 (2026-07-09, 보류)

- 현재 1차-A는 "못 한 것을 실패 처리하지 않고 재배치/축소/보류하는 루프"에 집중한다.
- reduce는 작게 줄이기 의미를 유지한다.
- 사용자가 컨디션이 좋거나 시간이 남을 때 기존 항목을 더 크게 확장하고 싶을 수 있다.
- 예:
  - "영어 단어 5개" -> "예문까지 10개 정리"
  - "자료구조 30분 보기" -> "연결 리스트 문제 3개 풀기"
  - "20:00-20:30" -> "20:00-21:00"
- UX 후보:
  - 항목 메뉴에 "더 해보기" 또는 "늘리기" 액션 추가
  - 시간 있는 항목에 "+30분" 퀵 버튼 제공
  - 모바일에서는 모달보다 빠른 퀵 액션 우선 검토
- 도메인 후보:
  - reduce와 통합한 rescale보다는 별도 expand/extend 액션 우선 검토
  - 이벤트 타입 후보: EXPANDED 또는 EXTENDED
  - SCALE_UP / SCALE_DOWN으로 일반화할지는 실제 사용 데이터 확인 후 판단
- 보류 이유:
  - 현재 1차-A 범위를 넘는다.
  - scale-up은 아직 실제 사용 필요성이 검증되지 않았다.
  - rescale로 미리 추상화하면 reduce/move/hold처럼 선명한 도메인 액션 경계가 흐려질 수 있다.
- 상태: **1차-A 완료 후 30일 자가사용 중 필요성 확인**

## 운영일과 달력 날짜 분리 (2026-08-03, 보류)

- 상태: **자가사용 중 자정 이후 일정이 반복될 때 검토**

## AI 응답 계약 경량화 (2026-08-06, 대화)

- 문제: 사용자 답변과 큰 구조화 데이터를 한 번에 생성하면 같은 내용이 중복되고, 기존 계획에서 일부만 바꾸는 요청에도 전체 계획을 다시 출력하게 된다. 출력 한도에 걸리면 JSON 전체가 불완전해질 수 있다.
- 현재 `max-completion-tokens=1200`은 자연어 답변과 구조화 JSON이 함께 쓰는 상한이다. reasoning 모델이 내부 추론에 큰 몫을 쓰면 사용자에게 보이는 답변이나 뒤쪽 JSON이 짧아질 수 있으므로, 파서나 스키마 기술만으로 해결됐다고 보지 않는다.
- AI는 편한 상담을 우선하며, 사용자가 계획 생성·조정을 명시적으로 요청하거나 동의했을 때만 계획 후보를 만든다.
- 현재 구현된 최상위 계약 `CHAT / OFFER / PROPOSAL`은 유지한다. `CHAT` 안에서 추가 질문을 할 수 있으므로 `ASK`를 당장 별도 타입으로 늘리지 않는다.
- 일반 상담과 추가 질문은 `CHAT`, 계획 정보는 충분하지만 사용자가 요청하지 않은 경우는 `OFFER`, 명시적 요청이나 동의가 있는 경우만 `PROPOSAL`을 사용한다.
- 계획 기능이 기존 계획 조정까지 확장될 때 `PROPOSAL`의 내용 또는 하위 종류를 다음처럼 나누는 방안을 검토한다.
  - `PLAN_DRAFT`: 새 계획을 처음 만들 때 새 항목 후보 전체를 반환
  - `PATCH`: 기존 계획을 조정할 때 바뀌는 내용만 반환
- `PATCH`의 동작 후보는 `CREATE`, `MOVE`, `REDUCE`, `HOLD` 등 현재 실행 조각 액션과 맞춘다. 여기서 `PATCH`는 HTTP 메서드가 아니라 AI 변경 제안 형식이다.
- 서버는 기존 데이터와 변경 명령을 결합해 변경 전후 미리보기를 만들고, 소유권·날짜·시간·상태 불변조건을 검사한다.
- AI 응답을 바로 공식 데이터에 반영하지 않는다. `AIProposal → 사용자 수정·선택 → 적용` 원칙을 그대로 유지한다.
- 제안 이후 사용자가 원본 계획을 수정한 경우를 막기 위해 `baseVersion` 또는 동일 목적의 버전 검사가 필요하다. 사용자가 직접 수정한 필드는 AI 재조정 시 기본 보호한다.
- 현재의 1회 호출 스트리밍은 자연어 답변 뒤 구분자와 JSON을 붙이고 서버가 파싱·검증하는 구조다. Spring AI에서 스트리밍과 `.entity()` 기반 구조화 출력을 같은 호출로 쓰기 어려워 채택한 현행 계약을 이 아이디어 때문에 바로 교체하지 않는다.
- Structured Outputs는 응답 형식을 고정하는 장기 후보지만 출력 한도 초과, 의미상 잘못된 값, 일정 충돌까지 해결하지는 않는다. 도입하더라도 작은 응답 계약과 서버 검증이 필요하다.
- 확장 판단: 기존 계획 조정은 변경점 `PATCH`, 새 계획 생성은 제한적으로 `PLAN_DRAFT`를 사용한다. 전체 기존 계획을 매번 재출력하는 방식은 기본값으로 삼지 않는다.
- 상태: **일반 AI 상담·계획 조정 계약을 확장할 때 승격 검토**

## 일정 계산·자연어 날짜 기술 후보 (2026-08-06, 기술 탐색)

- 장기 역할 분리 후보:
  - GPT: 사용자의 목표·제약·선호·변경 의도 해석
  - Spring 서버: 데이터 검증, 변경 전후 미리보기, 승인 적용
  - 일정 계산 엔진: 일정 충돌, 마감, 하루 상한, 기존 배치 유지 등을 계산
- `Timefold Solver`는 Java/Spring 환경에서 강한 규칙과 선호 규칙을 함께 다루는 일정 최적화 후보다. 실행이 밀렸을 때 완료된 조각은 고정하고 남은 조각만 다시 계산하는 방향과 잘 맞는다.
- `OR-Tools CP-SAT`도 복잡한 일정 최적화가 가능하지만 직접 제약 모델을 더 낮은 수준에서 구성해야 하므로 우선 후보는 Timefold다.
- `Natty`는 영어 자연어 날짜 표현을 실제 날짜·시간으로 바꾸는 보조 파서다. 한국어 중심 서비스에서 신뢰할 만한 핵심 날짜 엔진으로 사용하지 않는다.
- 한국어 날짜는 당분간 `java.time` 기반의 자주 쓰는 규칙과 GPT의 ISO 날짜 후보 추출을 조합하고, 서버가 `Asia/Seoul` 기준으로 검증한다. 모호한 표현은 자동 확정하지 않고 사용자에게 후보를 확인받는다.
- `Duckling`은 한국어 시간 규칙 후보지만 별도 실행 환경의 운영 부담이 있어 현재는 보류한다.
- `BAML`은 구조화 출력·테스트·모델 교체를 체계화하는 후보, `LangGraph`·`Temporal`은 장시간 AI 작업의 중단·재개와 장애 복구 후보로만 기록한다.
- Kafka·Redis·벡터 DB는 현재의 JSON 형식, 출력 토큰, 일정 계산 문제를 직접 해결하지 않으므로 이 문제의 해결책으로 도입하지 않는다.
- 상태: **승격(`03-planning-system.md`, `04-requirements.md`, `05-database.md`, `06-mvp-roadmap.md`) — 2026-08-06, Timefold Solver 2.4.0을 새 PROPOSAL 항목의 7일 범위 후보 배치 한 바퀴에 한해 도입했다.** 범위는 새 후보 배치 계산 하나로 좁게 유지했다: 기존 ExecutionItem을 옮기거나 줄이거나 보류하는 PATCH 재계획, ContextItem 기반 장기 자동 학습, 상시 자동 재계획(daemon/SolverManager), 실시간 ProblemChange 스트리밍은 이번에도 만들지 않았다 — 여전히 후속 범위다. `Natty`·`Duckling`·`BAML`·`LangGraph`·`Temporal`·Kafka·Redis·벡터 DB는 이 결정과 무관하게 계속 현재 구현 제외다.

## 설계 과밀화 방지 판정 (2026-08-06, 대화)

- 제품 비전과 `PlanItem → ExecutionItem → ExecutionRecord → ExecutionItemEvent` 분리는 과설계가 아니다. 계획, 실행 예정 조각, 실제 수행, 조정 사건은 제품의 핵심 질문에 각각 필요하다.
- `AI 제안 → 수정 → 승인 → 저장`, 오늘·계획·실행·기록의 책임 분리, 이동·축소·보류 이벤트 기록도 유지한다.
- 과설계가 되는 지점은 핵심 흐름을 실제로 끝까지 사용하기 전에 Timefold, Natty, BAML, LangGraph, Temporal, Kafka, Redis, 벡터 DB와 월간·연간 분석까지 동시에 구현하는 것이다.
- 지금 검증할 한 바퀴는 `상담 → 계획 초안/변경점 → 미리보기 수정 → 승인 → 계획·실행 반영 → 완료·부분 수행·미수행 기록 → 다음 상담 반영`이다.
- 현재 가장 큰 위험은 기능 부족보다 서로 다른 시기의 문서와 구현 범위를 한꺼번에 최신 설계로 오해하는 것이다. 장기 후보는 이 문서에 보관하고, 현재 구현 명세로 승격하기 전에는 필수 요구사항처럼 취급하지 않는다.
- 상태: **현재 구현 범위 판단 원칙으로 적용**
