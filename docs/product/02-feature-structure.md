# 02. Feature Structure

## 1. 전체 구조

diary-app은 화면 이름이 아니라 사용자 책임을 기준으로 나눈다.

```text
오늘     당일 실행과 재조정
계획     앞으로 할 일의 생성·검토·편집
실행     여러 날짜·시간에 배치된 조각의 운영
기록     실제 결과와 조정 이력의 확인

AI 패널  네 영역을 번역하고 연결
Quick    빠른 입력과 상담 진입
```

과목, 루틴, 회고, 통계는 중요한 기능이지만 최상위 탭을 계속 늘리지 않는다. 과목은 계획 생성에 필요한 구조화된 자료, 루틴은 반복 실행 원본, 회고·통계는 기록을 읽는 하위 보기로 배치한다.

## 2. 탭별 책임

### 2.1 오늘

오늘은 `오늘 날짜의 실행 작업면`이다.

- 오늘의 컨디션과 운영 강도
- 오늘 날짜의 실행 조각
- 현재 시각 기준 다음 행동
- 완료·부분 수행·미수행 기록
- 남은 오늘 다시 짜기
- 내일로 이동·축소·보류·다른 날짜 이동

오늘 화면은 장기 계획을 새로 설계하는 곳이 아니다. 필요한 경우 AI 패널을 통해 변경안을 만들고, 사용자가 승인한 당일 변경만 반영한다.

### 2.2 계획

계획은 `앞으로 무엇을 할지 만드는 작업 공간`이다.

- 자연어 요청과 계획 제목
- 기간·목표·제약·우선순위
- 날짜별·주차별·단계별·월별 그룹
- PlanItem 생성·수정·삭제·순서 변경
- 실행 조각 후보 미리보기
- 관련 컨텍스트 검토
- AI 초안 비교·선택 적용

계획은 아직 실제 수행 결과를 소유하지 않는다. 실제 결과는 기록에 남는다.

#### 2.2.1 자료·과목 (학습)

계획 탭의 "자료·과목" 서브탭은 강의계획서/교재/교수자료를 구조화된 학습 자료로 바꾸는
자리다(2026-08-09 확정). 세 개의 좁은 책임으로 나눈다.

- **Material Agent** — 업로드한 자료(PDF/PPTX)에서 실제로 무엇이 적혀 있는지 읽고 topic
  트리 초안을 만든다. 원문에 실제 있던 항목(SOURCE)과 AI가 학습 편의를 위해 세분화한 항목
  (AI_DERIVED)을 구분하고, 목차 근거가 없으면 지어내지 않는다. 사용자가 검토·수정한 뒤
  적용해야만 확정 topic 트리(및 과목의 교재 정보)가 바뀐다.
- **Learning Agent** — 확정된 topic 트리와 진행 상태(NOT_STARTED/IN_PROGRESS/LEARNED)를
  보고 개인과외 대화를 하고, 다음 학습(무엇을, WHAT)을 추천한다. 시간 배치는 하지 않는다.
- **Planning Agent** — Learning Agent의 추천을 받아 기존 실행/스케줄링 파이프라인
  (`ExecutionItem`, `AiProposal`, Timefold 기반 `SchedulePreviewService`)에 그대로 태워
  현실적인 시간 후보(언제, WHEN)를 만든다. 사용자가 검토·Apply해야만 `ExecutionItem`이 생기고,
  그 이후로는 오늘/실행 화면이 다른 AI 생성 조각과 동일하게 다룬다 — 학습 전용 원본을 따로
  두지 않는다.

실행 결과(완료)는 다시 topic 진행 상태로 돌아온다 — 단, "완료 버튼을 눌렀다"는 사실만으로
LEARNED(완전히 이해함)로 단정하지 않는다. 최종 LEARNED 처리는 항상 사용자가 학습 화면에서
직접 누르는 별도 액션이다.

### 2.3 실행

실행은 `여러 날짜에 걸친 조각을 배치하고 운영하는 화면`이다.

- 주간 목록과 시간표
- 날짜·시간·순서 배치
- 이동·축소·보류·재개·취소
- 루틴에서 생성된 조각 운영
- PlanItem별 실행 진행 상태
- AI 변경안의 ghost/diff 미리보기

오늘과 실행은 같은 `ExecutionItem`을 본다. 오늘은 날짜가 오늘인 항목만, 실행은 기간 전체를 보여준다.

### 2.4 기록

기록은 `실제로 일어난 사실과 변경 이유를 보는 화면`이다.

- 완료·부분 수행·미수행 결과
- 실제 수행 시간과 메모
- 이동·축소·보류·분할 이력
- 하루·주·월·학기·방학 단위 회고
- 반복되는 조정 패턴과 통계
- 다음 계획에 쓸 인사이트 후보

현재 상태와 과거 사건을 섞지 않는다. 상태는 ExecutionItem, 실제 결과는 ExecutionRecord, 조정 사건은 ExecutionItemEvent가 소유한다.

## 3. AI 패널 책임

AI 패널은 별도 데이터 보관함이 아니라 자연어와 제품 데이터를 잇는 번역 계층이다.

패널 입력:

- 사용자의 현재 요청
- 현재 선택한 계획 또는 실행 조각
- 관련된 사용자 확정 컨텍스트
- 필요한 범위의 실제 수행·조정 집계

패널 출력:

- PlanItem 후보
- ExecutionItem 생성·이동·축소 후보
- ContextItem 후보
- 변경 이유와 충돌 경고

AI가 보여준 초안은 공식 데이터가 아니다. 패널에서 수정하거나 화면에서 직접 편집한 뒤 `적용`해야 저장된다.

## 4. Quick 책임

Quick은 다음 동작의 짧은 진입점이다.

- 오늘 조각 빠른 추가
- 실제 수행 또는 상태 빠른 기록
- 짧은 고민 메모
- AI 상담 패널 열기

Quick 자체가 별도 원본 데이터를 만들지 않는다. 선택한 동작에 따라 오늘, 기록, 컨텍스트 후보 또는 AI 제안 흐름으로 연결한다.

## 5. 사용자의 하루 시나리오

1. 오늘 화면에서 컨디션과 오늘 조각을 확인한다.
2. 계획이 현실과 다르면 “남은 오늘 다시 짜기”로 AI 패널을 연다.
3. AI가 이동·축소·보류 후보를 화면에 미리 보여준다.
4. 사용자가 날짜·시간·분량을 직접 고치거나 대화로 다시 요청한다.
5. 필요한 항목만 적용한다.
6. 실행 중 완료·부분 수행·미수행을 기록한다.
7. 부분 수행이면 실제로 한 만큼을 기록하고 남은 분량을 새 실행 조각으로 만든다.
8. 기록 화면에서 오늘의 실제 결과와 조정 사건을 확인한다.
9. 다음 상담에서 확인된 제약과 실제 패턴이 다시 사용된다.

## 6. 사용자가 수정할 수 있는 지점

| 시점 | 직접 수정 | 대화 수정 |
| --- | --- | --- |
| 상담 결과 | 목표·제약·컨텍스트 후보 선택 | “알바 일정 반영해줘” |
| 계획 초안 | 제목·기간·순서·우선순위 | “첫 주 분량을 절반으로 줄여줘” |
| 실행 미리보기 | 날짜·시간·예상 분량 | “수요일 일정만 목요일로 옮겨줘” |
| 실행 중 | 완료·부분·미수행, 이동·축소·보류 | “오늘 남은 것만 다시 배치해줘” |
| 기록 후 | 실제 시간·메모·컨텍스트 확정 | “다음부터 알바 다음 날은 가볍게 잡아줘” |

## 7. 화면과 데이터 관계

| 화면 | 읽는 원본 | 주로 쓰는 원본 |
| --- | --- | --- |
| 오늘 | DailyState, 오늘 ExecutionItem | DailyState, ExecutionRecord, ExecutionItemEvent |
| 계획 | PlanItem, ContextItem, AIProposal | PlanItem, 선택 적용된 ContextItem |
| 실행 | 기간 내 ExecutionItem, 관련 PlanItem | ExecutionItem, ExecutionItemEvent |
| 기록 | ExecutionRecord, ExecutionItemEvent | 회고 메모, ContextItem 후보 |
| AI 패널 | 현재 선택 + ContextItem + 집계 | AIProposal/Item만 먼저 저장 |

## 8. “왜 이 조각인가” 경로

각 실행 조각은 가능한 경우 다음 경로를 보여준다.

```text
취업 준비 고민
→ 프로젝트 배포 목표
→ 평일 저녁 알바 제약
→ 이번 주 계획 항목
→ 오늘 가능한 크기로 축소
→ 로그인 오류 처리 1개
```

이를 위해 PlanItem/ExecutionItem과 ContextItem 사이의 연결 정보를 보존한다.

## 9. 충돌 해결 기준

- 오늘과 실행이 같은 항목을 따로 저장하지 않는다.
- 계획은 예정, 기록은 실제를 소유한다.
- AI 실시간 변화는 미리보기이며 자동 적용이 아니다.
- 과목은 계획 재료를 제공하지만 실행 결과를 별도로 소유하지 않는다.
- 루틴은 반복 원본이며, 특정 날짜에 생성된 결과는 ExecutionItem이다.
- 회고와 통계는 ExecutionRecord/Event를 읽어 해석하며 별도 완료 데이터를 만들지 않는다.
