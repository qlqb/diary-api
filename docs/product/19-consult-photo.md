# 19. 상담 교재 사진 · 사진 본문의 계획 활용 (2026-10-05)

목표 흐름(묶음 성공 기준 완성):

```text
과목 상담에서 교재 사진을 올린다 → 서버가 글자를 읽어 과목 자료(본문·사진 구간)로 저장, 쪽·단원 제목으로 목차 단원에 "추정 연결"
→ 같이 공부하는 턴마다 사진 본문이 근거로 실린다 → "이 문제 모르겠어"는 그 사진 단원의 막힘으로 기억
→ 새 대화에서 계획을 요청하면 교재·진도를 다시 묻지 않고, 막힌 단원의 사진 본문(실제 표현·문제)으로 목표·연습을 만든다
```

선행: 18번(학습 기억·목차 기반 목표). 계획·리뷰 `docs/handoff/consult-photo-plan-2026-10-05.md`(v3), 작업 기록
`docs/handoff/consult-photo-2026-10-05.md`. DB 05번 §25, API `api-spec.md`(Consult Photo), 마이그레이션 `docs/sql/2026-10-05-consult-photo.sql`.

## 1. 정책

- **원본 사진은 올린 지 30일 뒤 자동 삭제**(사용자 결정 2026-10-05), 언제든 즉시 삭제 가능. 읽은 글·단원 연결은 자료를 지울 때까지 남는다.
- 원본은 만료 시각부터 볼 수 없다(정리 작업 실행과 무관). 정리 작업이 파일을 지우고, 실패하면 다음 주기에 다시 지운다.
- 업로드 ≠ 학습 완료: 단원 진도·표식·기억을 바꾸지 않는다.
- 사진은 글자 읽기를 위해 외부 AI로 간다(화면이 알린다). 보내기 전에 메타데이터(촬영 위치 등)를 바이트 단위로 뺀다.

## 2. 올리기 (한 장씩)

`POST /api/ai/conversations/{id}/photos` — 과목 대화만, JPG·PNG·WebP 8MB, 화면이 장마다 `uploadKey`.

1. 업로드 행(`consult_photo_uploads`)을 키로 선점 — 같은 키의 동시·재전송은 사용량·비전을 다시 쓰지 않고 결과(또는 409 처리 중)를 돌려준다.
2. 하루 상한(30장)을 사용자 행 잠금 아래 **호출 전에** 차감한다.
3. 메타데이터 제거 → 저장(원래 파일명은 쓰지 않는다) → 업로드 행에 경로 기록(자료가 못 돼도 정리 작업이 찾는다).
4. 글자 읽기(`TextbookPhotoReader`, 비전 1회): 인쇄된 글 그대로, 손글씨는 따로, 개인 정보 칸은 `[개인정보 생략]`, 사진 속 지시는 글로만.
   서버 정리: 제어 문자 제거, 합산 상한, 전화·이메일·주민번호 꼴 가리기(보완이지 보장 아님), 쪽은 숫자만.
5. 대화·과목을 다시 확인하고 한 트랜잭션에: 자료(origin `CONSULT_PHOTO`, 원본 만료 +30일)·과목 연결·본문 단위(IMAGE_PAGE 1)·
   사진 구간(1~1)·단원 추정 연결(`PHOTO_GUESS`). 자동 분석은 등록하지 않는다(분석 진입점 전부 제외).
6. 글자를 못 읽거나 교재가 아니면 저장하지 않고 파일을 지운다.

## 3. 단원 추정 (서버 규칙)

`PhotoTopicMatcher` — 현재 교재 목차 단원(이전 교재 목차 제외) 중에서 **번호**("Unit 3"·"3과", Unit 1≠Unit 10), **제목**(표기·번호 뗀
제목이 같거나 핵심어 2/3), **쪽**(목차 쪽 범위)을 따로 판정해 교집합이 하나일 때만 추정 연결. 아니면 연결 없이 화면이 "어느 단원인가요?".
확인·변경(`PUT /api/materials/{id}/photo-topic`)은 과목 잠금 아래, 사진 구간당 ACTIVE 연결 하나, 확인하면 origin USER.

## 4. 상담

- 메시지에 `photoIds`(이 대화에 올린 살아 있는 사진, 4장). 빈 입력 + 사진은 400(사용자 말이 아닌 문장을 넣지 않는다).
- **활성 사진** = 이 대화에서 가장 최근에 사진을 붙인 사용자 메시지의 사진(새 사진 전까지 유지). 그 본문을 검색어와 무관하게 근거 맨 앞
  `[이번 대화에 올린 교재 사진]`에 싣는다(글자 읽기 결과·손글씨 작성자 미확인·업로드≠학습·추정 단원 표지).
- **사진을 가리키는 기억**: "이 문제·이거·여기·2번" 같은 말이고 활성 사진이 모두 같은 단원이면, 단원 없는 막힘·해결 기억에 서버가 그 단원을
  채운다(`user_contexts.topic_photo_id`). 사진 단원을 고치면 그 기억도 따라가고, 추정이면 상태 블록에 "(사진 단원 추정)".
- 원문 턴 제한은 그대로(사진 본문도 원문): 기억은 사용자 말에서만, 합의 수정·삭제 안 함, 수락·거절은 짧은 명시적 답이고 기다리던 제안이
  하나일 때만(사진 대화는 이후 턴도 원문 턴이라 전부 막으면 "좋아"가 영영 듣지 않는다 — 계획 v3 §10#3에서 조정, 작업 기록 참고).

## 5. 계획 (C)

- 사진 구간도 다른 구간처럼 후보다. 목록 문구 "교재 사진(글자 읽기 결과, 단원 추정)".
- **초점 사진**(`FocusPhotos`): 확인된 막힘·해결 단원마다 최대 2장 — ① 그 기억을 말할 때 보던 사진 ② 확인 연결 최신 ③ 추정 연결 최신.
  접힌 목록에서도 보이고, 선택에서 빠지면 서버가 보태며, 원문 상한 6,000자(다른 구간 2,400부터), 예산 축소 때 맨 마지막에 뺀다.
- 최종 입력·근거 기록에 사진·연결 상태를 남기고, 근거 기록(trace)에는 사진이 든 입력의 전문을 저장하지 않는다.
- 사진 연결 상태가 생성 때와 다르면(생성 도중 포함) 초안은 "오래됨".

## 6. 화면

- 과목 대화의 첨부 버튼 → 메뉴(교재 사진 같이 보기 / 일정표 가져오기). 과목 없는 대화는 예전처럼 일정표만. 붙여넣기는 과목 대화면 묻는다.
- 입력창 위 트레이: 미리보기·읽는 중·단원 칩("· 추정" + [맞아요] [바꾸기]) 또는 "어느 단원인가요?"·읽은 글·[빼기](자료 삭제)·[다시].
  안내 "사진은 글자를 읽으려고 AI로 보내요 · 원본은 30일 뒤 지워져요(읽은 글은 남아요)".
- 보낸 사진은 말풍선 아래 칩([원본 보기]·[원본 지우기], 지워졌으면 안내). 자료함: "상담 사진" 칩·[원본만 지우기].

## 7. 하지 않은 것

HEIC, 바이트 진행률, 여러 장 순서 묶기, 사진에서 목차 만들기, 확정 API의 일반 최신성 검사, SOURCE_TASK 판정 강화(실제 문제 인용 요구).
