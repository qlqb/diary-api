# 10. 핵심 사용자 경험과 컨텍스트 구조

> 상태: 제품 경험 기준 문서
> 작성일: 2026-08-10

이 문서는 diary-app이 궁극적으로 어떤 경험을 제공해야 하는지 정리한다.
세부 화면, API, DB 구조보다 상위에 있는 제품 판단 기준으로 사용한다.

---

## 1. 한 문장 정의

사용자는 매번 자신의 자료와 상황을 AI에게 처음부터 설명하지 않는다.
주제별로 축적된 자료, 확정된 상태, 이전 실행 결과를 AI가 이미 참고할 수 있고,
사용자가 자연어로 요청하면 그 맥락을 바탕으로 현실적인 계획 초안을 만든다.
초안은 채팅 문장으로 끝나지 않고 캘린더·주간계획 등 수정 가능한 화면으로 나타나며,
사용자가 직접 고치고 확인한 뒤에만 실제 일정과 오늘 실행 항목에 반영된다.
실행 결과는 다시 다음 AI 판단에 사용된다.

핵심 흐름은 다음과 같다.

```text
자료와 상태가 축적됨
→ AI와 자연스럽게 대화
→ AI가 현재 상황을 해석
→ 수정 가능한 계획/행동 초안 생성
→ 사용자가 화면 또는 대화로 수정
→ 사용자 확인
→ 실제 일정/오늘에 반영
→ 실행
→ 결과 기록
→ 다음 AI 판단에 재사용
```

---

## 2. 사용자가 실제로 원하는 역할

사용자의 주된 역할은 자료와 상태를 일일이 구조화하는 것이 아니다.

사용자는 주로 다음 행동을 한다.

```text
자료를 넣는다.
상황을 말한다.
AI와 생각한다.
AI가 만든 초안을 확인하고 고친다.
실제로 실행한다.
```

파일 분류, 검색용 색인, 필요한 컨텍스트 조합 등은 가능한 한 앱과 AI가 뒤에서 처리한다.
사용자가 폴더, 태그, 학습지도를 완벽하게 관리해야만 AI가 제대로 작동하는 구조는 피한다.

---

## 3. 주제별 컨텍스트 공간

사용자는 필요에 따라 주제별 공간을 만들 수 있다.
이 공간은 대학 과목에만 한정하지 않는다.

예:

```text
내 학습/작업 공간
├ 자료구조
├ 네트워크 프로그래밍
├ 토익
├ 정보처리기사
└ 개인 프로젝트
```

각 공간은 해당 주제에 대해 AI가 지속적으로 참고할 수 있는 컨텍스트 경계다.

예를 들어 `자료구조` 공간에는 다음 내용이 축적될 수 있다.

```text
Sources
- 강의계획서.pdf
- 연결리스트.pptx
- 트리.pdf
- 교재 목차.pdf

Confirmed State
- 현재 학습: 연결 리스트
- 중간고사: 8월 28일
- 과제 마감: 8월 20일
- 사용자가 어렵다고 확인한 부분: 포인터 삭제 과정

Execution History
- 연결 리스트 복습 계획 50분
- 실제 수행 30분
- 결과: 일부 진행
```

공간은 사용자에게는 폴더처럼 이해하기 쉽게 보일 수 있지만,
내부 데이터 모델에서 파일의 절대 소유권까지 폴더 구조에 묶을 필요는 없다.
하나의 자료를 여러 맥락에서 참조해야 하는 경우를 막지 않는다.

---

## 4. 파일과 DB 상태는 역할이 다르다

### 4.1 파일은 근거 자료다

PDF, PPT, 문서, 메모 등은 원본 Source로 보존한다.
파일을 추가했다고 모든 내용을 즉시 Topic, PlanItem, ExecutionItem 등으로 변환하지 않는다.

파일이 추가되면 해당 공간의 AI가 필요할 때 관련 내용을 찾아 참고할 수 있어야 한다.

예:

```text
"교수님 자료 기준으로 트리 순회를 설명해줘."
"중간고사 범위가 어디까지야?"
"이 PPT에서 연결 리스트 삭제 부분을 다시 찾아줘."
```

별도의 거대한 `분석 완료` 절차가 대화의 선행 조건이 되어서는 안 된다.

### 4.2 DB는 오래 유지해야 하는 상태다

AI가 빠르게 알고 있어야 하고 다음 행동에 실제 영향을 주는 확정 상태는 DB에 보존한다.

예:

- 사용자가 확정한 시험·과제 일정
- 현재 학습 진도
- 사용자가 직접 확정한 목표와 제약
- 적용된 계획
- 실제 실행 결과
- 반복적으로 다음 판단에 필요한 상태

AI가 한 번 추론했다는 이유만으로 불확실한 정보를 영구 사실처럼 저장하지 않는다.
원본 근거와 사용자 확정을 구분한다.

즉 다음 두 가지를 분리한다.

```text
Source
= AI가 필요할 때 찾아보는 근거

Confirmed State
= 다음 계획과 실행에 지속적으로 사용되는 현재 상태
```

---

## 5. AI가 읽는 것과 앱 상태를 바꾸는 것은 다르다

AI가 자료를 읽고 답변하는 데에는 별도 승인이 필요하지 않다.
하지만 AI의 판단이 실제 앱 상태를 변경하는 순간에는 사용자의 확인이 필요하다.

```text
자료를 읽고 질문에 답하기
→ 즉시 가능

자료를 바탕으로 학습 후보 제안
→ 초안

이번 주 계획 생성
→ 초안

실제 일정 생성
→ 사용자 확인 후 반영

ExecutionItem 생성/이동/축소
→ 사용자 확인 후 반영
```

제품 전체에서 다음 경계를 유지한다.

```text
AI가 이해함 ≠ 앱 상태가 변경됨
AI가 제안함 ≠ 실제 일정에 적용됨
```

## 6. 상위 통합 계획 경험

각 공간은 독립적인 자료와 상태를 가지지만,
사용자의 실제 시간은 하나이므로 상위 계획 단계에서는 여러 공간을 함께 본다.

예:

```text
자료구조
- 연결 리스트 진행 중
- 중간고사 D-12
- 다음 학습 후보 40분

네트워크 프로그래밍
- UDP 미학습
- 과제 D-5
- 다음 학습 후보 50분

토익
- 단어 복습 지연
- 복습 후보 30분

개인 상태
- 이미 잡힌 수업/약속
- 반복 일정
- 사용할 수 있는 시간
- 최근 실제 수행량
```

사용자는 이를 일일이 조합하지 않고 자연어로 요청한다.

```text
"이번 주 공부 계획 짜줘."
```

AI는 여러 공간의 상태와 사용자의 현실 제약을 함께 참고해 계획 초안을 만든다.

---

## 7. 계획은 반드시 시각적인 초안으로 나타난다

AI가 계획을 긴 채팅 답변으로만 제공하고 끝내지 않는다.
계획 결과는 사용자가 실제로 검토할 수 있는 화면으로 변환한다.

예:

```text
이번 주 계획 초안

월 14:00-14:40  자료구조 · 연결 리스트 복습
화 13:00-13:30  토익 · 단어 복습
수 15:00-15:50  네트워크 · UDP 학습
금 14:00-15:00  자료구조 · 트리 입문
```

표현 방식은 주간 캘린더, 시간표, 목록 등이 될 수 있다.
중요한 것은 사용자가 계획의 날짜, 시간, 분량, 순서를 눈으로 보고 직접 수정할 수 있다는 점이다.

사용자는 두 방식으로 수정할 수 있어야 한다.

- 화면에서 직접 이동, 시간 변경, 축소, 삭제
- AI에게 자연어로 다시 조정 요청

예:

```text
"수요일은 너무 빡세니까 네트워크를 금요일로 옮겨줘."
```

수정 결과도 다시 초안으로 보여준다.

---

## 8. 확인 전에는 실제 일정이 아니다

계획 초안은 실제 실행 데이터와 분리한다.

```text
AI 계획 생성
→ 미리보기
→ 사용자 수정
→ 사용자 확인
→ 실제 일정/실행 항목 생성
```

사용자가 확인한 뒤에만 실제 ExecutionItem 등 실행 데이터가 생성되거나 변경된다.

이 원칙은 AI가 사용자 대신 중요한 결정을 확정하지 않도록 하는 안전장치이면서,
제품의 핵심 사용자 경험이기도 하다.

---

## 9. 일정에서 오늘로, 오늘에서 기록으로

확정된 주간 계획은 시간이 지나면서 자연스럽게 오늘의 실행으로 내려온다.

```text
주간 계획
수요일 15:00 네트워크 · UDP 학습

↓ 수요일

오늘
15:00 네트워크 · UDP 학습 50분
```

사용자는 실제 결과를 남긴다.

```text
완료
일부 수행
이동
축소
보류
```

실제 결과는 기록으로 남고, 관련 공간의 상태와 다음 AI 판단에 반영된다.

예:

```text
계획: UDP 학습 50분
실제: 25분 수행
결과: 일부 진행

↓

다음 계획에서는
"지난번에 끝내지 못한 UDP 학습을 30분 이어서 진행"
같은 판단이 가능해진다.
```

## 10. 화면 영역의 책임

현재 제품 경험 기준에서 주요 영역의 책임은 다음처럼 본다.

### 학습/주제 공간

- 관련 Source를 모은다.
- 해당 주제에 대한 AI 대화를 한다.
- 현재 상태와 중요한 정보를 확인한다.
- 다음 학습/행동 후보를 만든다.

학습지도 같은 전체 구조 시각화는 필요할 때 제공할 수 있는 보조 뷰이며,
제품의 필수 진입 절차로 두지 않는다.

### 일정

- 여러 공간에서 나온 행동을 현실 시간에 배치한다.
- 시간 미정 후보와 확정된 시간 블록을 함께 다룬다.
- AI 계획 초안을 시각적으로 검토하고 수정한다.

### 오늘

- 지금 실제로 실행할 항목을 보여준다.
- 완료, 일부 수행, 이동, 축소, 보류 등 현재 조정을 담당한다.

### 기록

- 실제로 일어난 결과를 보존한다.
- 이후 AI 상담과 다음 계획이 참고할 근거가 된다.

## 11. 대표 사용자 시나리오

```text
1. 사용자가 자료구조 공간에 강의계획서와 교수 PPT를 넣는다.

2. 별도 분석 의식 없이 AI에게 질문할 수 있다.
   "이번 수업에서 연결 리스트 어디까지 했어?"

3. 사용자가 공부하고 현재 진도나 어려운 부분이 확정되면 상태로 남는다.

4. 네트워크, 토익 등 다른 공간에도 자료와 상태가 쌓인다.

5. 사용자가 상위 AI에게 말한다.
   "이번 주 공부 계획 짜줘."

6. AI는 각 공간의 현재 상태, 시험/과제, 기존 일정,
   최근 실행 결과를 함께 참고한다.

7. AI가 주간 계획 초안을 만든다.

8. 앱은 이를 캘린더/시간표/목록 형태로 보여준다.

9. 사용자는 직접 수정하거나
   "수요일은 너무 빡세니까 조금 줄여줘"라고 요청한다.

10. 사용자가 확인을 누른다.

11. 확정된 항목이 실제 일정과 오늘 화면에 반영된다.

12. 사용자가 실행 결과를 남긴다.

13. 다음 계획에서 AI는 그 결과를 다시 참고한다.
```

---

## 12. 현재 확정하지 않는 것

이 문서는 사용자 경험의 방향을 고정하기 위한 문서이며,
다음 구현 세부사항을 미리 확정하지 않는다.

- Source 검색을 어떤 Vector DB/RAG 기술로 구현할지
- 파일 저장소를 로컬, S3, MinIO 중 무엇으로 운영할지
- 주제 공간을 DB에서 정확히 어떤 테이블 이름으로 표현할지
- 모든 자료를 사전 구조화할지, 필요 시 추출할지의 세부 정책
- 학습지도를 어떤 형태로 제공할지 또는 유지할지
- 캘린더 미리보기의 최종 UI

이 항목들은 실제 사용 흐름을 구현하고 검증하면서 결정한다.

## 13. 기능 판단 기준

새 기능이나 화면을 추가하기 전에 다음을 확인한다.

1. 사용자가 AI에게 같은 상황을 반복 설명하는 일을 줄이는가?
2. AI가 자료와 확정된 현재 상태를 적절히 함께 사용할 수 있게 하는가?
3. AI의 답변이 채팅에서 끝나지 않고 수정 가능한 결과로 이어지는가?
4. 사용자가 실제 반영 전에 내용을 검토하고 수정할 수 있는가?
5. 계획이 오늘 실행으로 자연스럽게 이어지는가?
6. 실제 실행 결과가 다음 판단에 다시 쓰이는가?
7. 사용자가 내부 데이터 구조를 관리해야만 기능이 작동하는 부담을 만들고 있지는 않은가?

최종적으로 가장 중요한 질문은 다음이다.

> **이미 내 자료와 상황을 알고 있는 AI와 대화했을 때, 그 결과가 눈에 보이는 계획으로 나타나고, 내가 고친 뒤 실제 생활에 적용되며, 그 실행 결과까지 다음 판단에 기억되는가?**
