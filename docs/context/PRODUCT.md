# PRODUCT — diary-app 통합 기획서 v7.0

> 기준일 2026-11-01. 사용자가 쓴 「통합 기획서 v6.2(2026-07-31)」를 현재 코드(diary-api·diary-ui `dev-playground`)와 대조해 다시 쓴 판이다.
> v6.2는 이 문서로 대체한다(보관용). 제품 원칙·화면 책임·AI 승인 경계·결정 현황을 한 장에 모은다.
> 사실의 기준은 **코드 > `docs/product`(01~21) > 이 문서** 순이다. 표·열은 [SCHEMA](SCHEMA.md), 상태값은 [DOMAIN](DOMAIN.md), 경로는 [API](API.md).

## 1. 제품 한 문장과 핵심 흐름

자료·상담·실행 기록으로 사용자의 현실(시간·진도·막힘·시험 범위)을 모으고, 그 위에서 기간 계획 초안을 만들며,
사용자가 확인한 것만 오늘의 실행과 기록으로 이어 가는 개인 계획 운영 웹 앱이다. 실행 결과는 다음 계획을 바꾼다.

```text
자료를 올린다 · 상담에서 상황을 말한다(사진 포함)
→ 앱이 진도·시험 범위·막힘·해결을 기억한다
→ 계획을 요청하면 요청 범위·말한 시간을 원문과 대조해 기간 계획 초안을 만든다
→ 사용자가 초안을 고치고 확정한다 → 실행 조각이 오늘·일정에 배치된다
→ 완료·부분 수행과 이동·축소·보류가 기록된다 → 다음 상담과 계획이 그 기록을 쓴다
```

판단 기준: 새 화면·기능·테이블·인프라는 "자연어 상황 → 고칠 수 있는 초안 → 사용자 승인 → 실행과 기록 → 다음 계획"에 직접 기여할 때만 서두른다.

## 2. 변하지 않는 원칙

1. 머릿속·대화에만 있는 상황을 다시 볼 수 있는 구조로 꺼낸다.
2. AI는 결정을 대신하지 않고 사용자가 고칠 수 있는 초안을 만든다. 화면 직접 수정과 대화로 다시 조정하기 둘 다 된다.
3. 실행 원본은 하나다. 오늘·일정·계획·기록이 같은 `ExecutionItem`을 각자 관점으로 보여주고 따로 저장하지 않는다.
4. 계획 의도(예정)·실제 결과(`ExecutionRecord`)·조정 사건(`ExecutionItemEvent`)을 분리한다. 실제값으로 원래 계획을 덮어쓰지 않는다.
5. 미완료를 실패 한 칸으로 끝내지 않고 이동·축소·보류·남은 조각으로 이어 간다. 한 번의 편차는 기록만, 반복될 때만 기억·계획 변경을 제안한다.
6. 사용자 원문이 AI 정리보다 우선한다. 사용자가 말한 범위·시간은 서버가 원문과 대조하고, 근거 없는 정리는 후보로만 다룬다.
7. 산수는 언어모델에 맡기지 않는다. 가용시간·예산·배치는 서버 계산(Timefold 포함)이다.
8. 배치하지 못한 것은 숨기거나 억지로 채우지 않고 이유와 함께 보여준다.
9. 화면 문구는 평가가 아니라 사실과 선택지로 쓴다("실패·못 함·부족"을 기본 라벨로 쓰지 않는다).

## 3. 대상과 범위

- 1차 사용자: 수업·알바·개인 프로젝트·취업 준비를 함께 운영하는 대학생 개발자(개발자 본인). 첫 사용 사례는 과목·학기 운영이고, 같은 흐름을 **프로젝트** 단위로 개인 개발·자격 준비에도 쓴다.
- 이 앱이 아닌 것: 단순 Todo 앱, 자동 배치 캘린더, 일기 앱, AI 답변 보관함, 사용자 확인 없이 일정을 바꾸는 자율 스케줄러, 완료율로 압박하는 체크리스트, 수면·감정·지출 분석 플랫폼.
- 현재 도입 근거 없음(필요가 확인되면 재검토): Redis·Kafka·벡터 DB·다중 에이전트·MCP 우선 사용·소셜/템플릿 공유·수면/감정/지출 교차 분석.

## 4. 화면 구조

최상위 탭은 **6개**다(diary-ui `src/shell/MainShell.jsx`). v6.2의 4탭(오늘·계획·실행·기록)에서 바뀌었다 — "실행"은 "일정"이 되었고, 과목은 "프로젝트" 탭으로 올라왔으며, 자료가 독립 탭이 됐다.

| 탭 | 답하려는 질문 | 주 데이터 |
|---|---|---|
| 오늘 | 지금 무엇을 하고 남은 오늘을 어떻게 조정하지? | 오늘 날짜의 `execution_items`, 과제 마감 한 줄, 지난 수업 확인 카드 |
| 자료 | 무엇을 올렸고 분석은 어디까지 됐지? | `materials`, 자동 분석 작업·자료 구간 |
| 프로젝트 | 이 프로젝트에서 무엇을 배우고 어디까지 왔지? | `courses`·`course_topics`(교재 목차), `user_contexts`(기억), 정리안 |
| 계획 | 앞으로 무엇을 어떤 기간·순서로 하지? | `ai_proposals`(초안), `plan_versions`(확정·회고), 미배치 항목 |
| 일정 | 여러 날짜·시간에 어떻게 배치하지? | 기간 내 `execution_items`, `routines`(시간표), `one_off_commitments` |
| 기록 | 실제로 무엇이 일어났고 왜 달라졌지? | `execution_records`, `execution_item_events` |

- **AI 상담 패널**은 탭이 아니라 어느 탭에서나 여는 전역 도구다. 상단에 현재 상담 범위(프로젝트·이번 주 일정·오늘 실행 등)를 보여준다.
- 일기 API는 서버에 있지만 메인 화면에는 없다.
- **오늘 vs 일정**: 시간 범위와 주 용도가 다를 뿐 **행동을 인위적으로 막지 않는다.** 일정 탭에서도 완료·부분 수행을 기록할 수 있다(`ScheduleView`). 오늘은 "지금 실행·남은 오늘 다시 짜기", 일정은 "여러 날 배치·이동·축소·보류·시간표 편집"이 대표 행동이다.
- **패널과 변경 표시**: 상담이 만든 변경 묶음 카드는 패널 안에서 선택·적용한다. 계획 초안은 계획 탭에서 검토하고 일정 주간 표에 겹쳐 보인다. v6.2의 "패널은 변경 내용을 렌더링하지 않는다"는 폐기했다.
- 배치 표현: 날짜·시각 없음(`UNSCHEDULED`)은 계획 탭, 날짜만(`DATE_ONLY`)은 주간 표의 "하루 종일" 줄, 시각까지(`TIME_FIXED`)는 시간 칸에 보인다.

## 5. AI 역할과 승인 경계

### 5.1 AI가 하는 것 / 하지 않는 것

- 한다: 상담(감정 정리가 먼저면 행동 추천을 서두르지 않음), 구조화(사실·해석·변경안·기억), 제안, 근거 설명, **조회와 가정 계산**(일정·할 일·과제 조회, 가정 가용시간).
- 하지 않는다: 공식 데이터를 직접 쓰기, 사용자가 말하지 않은 원인·감정을 사실로 저장, 모든 고민을 할 일로 변환, 한 번의 사건을 장기 선호로 승격.

### 5.2 무엇에 승인이 필요한가 (2026-11-01 확정)

| 대상 | 규칙 |
|---|---|
| 계획·일정·실행·과제 같은 **공식 데이터 변경** | 사용자가 검토·선택·적용해야 바뀐다(사전 승인) |
| 사용자가 **직접 말해 원문으로 확인된 사실**(진도·시험 범위·막힘·해결·목표·제약 등) | 승인 팝업 없이 기억(`user_contexts`, 출처 `CONSULT_AUTO`)에 저장하고, 출처와 함께 보여주며 사용자가 고치기·확인·철회한다(사후 정정) |
| 적용 전 변경 묶음에 담긴 내용 | 사실 기억으로 저장하지 않는다 |
| 조회·비교·가정 계산·추천 표시 | 승인 없이 한다. 승인 규칙 때문에 매번 멈추지 않는다 |
| 대화 원문·임시 초안·작업 상태 | 저장한다(공식 데이터가 아니다) |

v6.2의 "기억은 후보로 보여주고 승인 후 저장"은 위 규칙으로 대체했다. AI의 **해석**과 반복 패턴을 기억으로 올리는 규칙은 미결(§10.4).

### 5.3 변경이 공식 데이터에 닿는 경로

| 경로 | 저장소 | 적용 |
|---|---|---|
| 기간 계획 초안 → 확정 | `ai_proposals`/`_items` → `plan_versions` + `execution_items` | `POST /api/plans/proposals/{id}/confirm`. 연결된 변경 묶음을 먼저 적용 → 일정 겹침 재검증 → 제안 적용 → 계획 판 삽입, 한 트랜잭션 |
| 상담 변경 묶음 (2026-10-26) | `ai_change_bundles`/`_items` | 패널 카드에서 선택 → `POST /api/ai/change-bundles/{id}/apply`. 루틴 회차 제외·이동, 약속, 할 일(완료 포함), 과제 마감 |
| 오늘 조정 등 일반 AI 제안 | `ai_proposals` | `POST /api/ai/proposals/{id}/apply` |
| 일정 후보(근무표·시간표 이미지, 상담) | `ai_schedule_suggestions` | 카드 승인, 일괄 적용은 한 트랜잭션 |
| 상황 변경 후보 | `ai_context_change_suggestions` | 카드 승인 |
| 롤링 배치 | (계산 결과를 바로 반영) | `POST /api/plans/{id}/place` — 확정된 계획의 다가온 7일에 시각을 정한다. 확인 없이 적용, `unschedule`로 되돌림 |

상담 턴: 도구 단계(조회·`propose_change`·`set_study_time`·`preview_availability`) → 답변 단계. 도구 결과는 턴 작업 공간에만 있다가 턴이 성공할 때만 묶음·합의로 저장된다. 응답은 SSE 스트림이고 같은 멱등 키 재전송은 저장된 턴을 재생한다.

### 5.4 선택 적용 규칙

- 사용자는 항목을 골라 **한 번에** 적용한다. 고른 항목은 한 트랜잭션, 하나라도 실패하면 전부 롤백.
- 고른 항목은 `APPLIED`(수정했으면 `MODIFIED_APPLIED`), 고르지 않은 항목은 `DISMISSED`로 끝난다. 같은 제안을 나눠 다시 적용하지 않는다. `PARTIALLY_APPLIED`는 없다. 남은 것을 쓰려면 현재 데이터로 새 제안을 만든다.
- 서로 기대는 항목: 변경 묶음은 고른 항목이 고르지 않은 항목에 기대면 409로 막는다. 추론한 연결은 기본 선택하지 않는다.
- 항목이 여럿이면 카드마다 적용 버튼을 두지 않고 적용은 하나다(단일 항목은 예외).
- 사용자가 직접 고친 값은 AI 원안과 구분한다.

### 5.5 우선 조각과 추천

저장된 중요도(`priority` MUST/SHOULD/OPTIONAL)와 순서(`order_index`)는 사용자가 정하거나 승인한 값이다. 마감·남은 시간·선행 작업을 반영한 **추천 표시**는 허용하되 저장된 중요도를 바꾸지 않는다 — 바꾸려면 변경안을 거친다. (원칙 채택 여부 미결, §10.4)

## 6. 계획과 현실이 달라질 때

대표 상황: 진행 없음 · 일부 수행 · 예상보다 많이/오래/빨리 · 시간은 채웠지만 목적 미달 · 다른 방식·다른 날·다른 행동으로 수행 · 외부 사정 · 컨디션 축소 · 우선순위 교체 · 필요 소멸 · 목표 자체 변경 · 기록 불확실.

처리 원칙:
- 원래 계획은 과거의 의도로 남긴다. 실제 결과는 별도 기록, 앞으로의 변경은 새 변경안으로 다시 승인받는다.
- 부분 수행은 기존 항목 전체를 옮기지 않는다. 한 만큼 기록하고 남은 부분만 새 조각으로 만든다.
  - 현재 코드: `recordPartial` = 원본 `DONE` + `PARTIAL` 기록(완료 1~99%) + 남은 조각(예상 시간 × 남은 비율, 최소 5분) + `REDUCED` 이벤트. 사용자가 입력한 완료 비율 기준이지 실제 시간 차감이 아니다.
  - 학습·개발의 남은 작업량은 비율로도 정확하지 않을 수 있다. 상담에서 다시 추정할지는 실사용으로 판단한다.
- 외부 원인과 자발적 미룸은 다른 신호다. 불확실한 값은 "약·추정·미확인"으로 둔다.
- 기록 이유: `execution_records`의 `blocker_kind`·`support_level`·`stuck_step`.

## 7. 프로젝트·자료·학습

과목을 최상위 메뉴에서 없애는 것과 과목 데이터를 없애는 것은 다르다 — 지금은 **프로젝트**(`courses`)가 관리 단위다.
자료 업로드(PDF·PPTX·HWP·HWPX·IPYNB·C++·ZIP·사진) → 자동 분석(자료 구간·토픽 연결·과제 후보) → 교재 목차(업로드 또는 웹 검색) → 프로젝트 정리안(사용자 적용) → 학습 기억·학습 이벤트(진도는 원천을 가리키는 이벤트로 쌓음) → 계획 초안이 이를 근거로 쓴다.
현재 주차와 실제 진도는 따로 다룬다. 수업에서 실제로 다룬 범위는 지난 수업 확인 카드로 정정한다. 상세는 `docs/product` 15~20번.

## 8. 데이터 모델 (현재)

```text
courses(프로젝트) ─ course_topics · materials · user_contexts · learning events
ai_proposals(초안) ─확정→ plan_versions(불변 스냅샷, plan_key+version)
                         └→ execution_items  실행의 유일한 원본
                              ├ execution_records      실제로 무엇을 했나
                              └ execution_item_events  계획을 어떻게 조정했나
routines(시간표·반복) · one_off_commitments(약속) · course_assignments(과제)
ai_conversations → messages → (drafts, change_bundles, proposals, schedule/context suggestions)
```

상태값·분류 enum(배치·실행 상태·결과·이벤트·중요도·출처·제안·변경 묶음·기억)은 [DOMAIN.md](DOMAIN.md)가 소유한다. 여기에 다시 적지 않는다.

마감 `execution_items.deadline_at`은 배치의 HARD 제약이고, 마감 안에 넣을 시간이 없으면 미배치로 남긴다.

v6.2 이름과의 차이: `plans`/`plan_items` → `plan_versions`, `context_items` → `user_contexts`, `TIME_BLOCK` → `TIME_FIXED`, `HIGH/NORMAL/LOW` → `MUST/SHOULD/OPTIONAL`, `display_order` → `order_index`, `estimated_minutes` → `expected_minutes`, `item_type` 없음, `ai_proposal_items`는 이미 정규화됨. Todo·ScheduleBlock·plan_items·plan_item_events는 2026-08-23에 제거했다. `is_fixed`/`flexibility` 열은 없다(UI 타입의 `isFixed`는 항상 false).

## 9. 기술과 신뢰성

- 스택: React 19 + Vite 7 + Tailwind 4 / Java 21 · Spring Boot 4 · Spring Security + JWT · MyBatis(JPA 없음) · Spring AI 2.0(OpenAI) · Timefold 2.4 / MySQL·MariaDB(마이그레이션은 `docs/sql` 수동 적용).
- AI 키는 서버에만. 모델 이름은 설정값. `AI_PROVIDER=none`이면 AI 경로만 503.
- 소유권: 모든 조회·수정에 `user_id` 조건.
- 동시성: `version` 열이 있는 표는 `version` CAS(불일치 409), 상태 전이는 조건부 UPDATE(`WHERE status = …`, 0행이면 409)나 `FOR UPDATE` 뒤 확인으로 보호하는 것이 규칙이다(CONVENTIONS.md). 이 규칙을 지키지 않는 상태 갱신이 남아 있다 — 2026-11-02 전수 확인(목록과 현황은 07번, 근거는 `docs/handoff/state-transition-audit-2026-11-02.md`). 변경 묶음은 revision·멱등 키·범위 지문(검토 뒤 일정이 바뀌면 STALE 409)까지 본다.
- **시간 겹침 재검증**: `version`은 같은 항목을 두 번 고치는 것만 막고, 서로 다른 항목이 같은 시간으로 가는 것은 못 막는다. 계획 확정은 약속·시각 있는 조각·반복 일정을 잠금 조회로 다시 읽어 하나라도 겹치면 전체를 거절한다(`PlanConfirmScheduleGuard`). **상담 변경 묶음과 일반 AI 제안 적용에는 이 검사가 없다**(미결 §10.4).
- 실패: 생성 실패 시 입력 보존·재시도, 파싱 실패 시 적용 가능한 제안을 만들지 않음, 충돌 시 "변경안을 만든 뒤 원본이 바뀌었어요" + 다시 계산. 서버 오류 코드를 그대로 노출하지 않는다.
- AI 입력 최소화: 요청에 필요한 계획·제약·최근 결과·근거만 싣는다. 일기 원문은 사용자가 첨부할 때만.
- 검증: 프런트 `npm run lint` · `npm test`(vitest) · `npm run build`, 백엔드 `./gradlew test`. 트랜잭션·권한·동시성을 건드리면 그 경로의 테스트를 함께 쓴다. lint·build·compile 통과만으로 끝내지 않는다.

## 10. 결정 현황 (2026-11-01 v6.2 대조)

### 10.1 확정

- 6탭 구조, 실행 원본 단일화, 예정·실제·조정 분리, 선택 적용 원자성, AI 공식 데이터 직접 쓰기 금지
- 기억 자동 저장(§5.2) — 사용자 발화 사실은 원문 대조 후 저장, 사후 정정
- 오늘·일정의 행동 제한 없음, 패널에서 변경 묶음 카드 표시 허용
- 배치 못 한 항목은 이유와 함께 표시(이미 구현: 초안 미리보기 "배치 안 됨 · 이유", 롤링 배치 결과 "N개는 시각을 정하지 못했어요")

### 10.2 폐기 (v6.2에서 걷어낸 것)

- 4탭 고정, "실행 탭에서 결과 기록 금지"와 그것을 prop 차단으로 강제하는 설계
- "패널은 변경 내용을 그리지 않는다" 절대 금지
- 검토 위치 규칙 "하루 안·2개 이하는 제자리, 3개 이상은 계획 탭"(항목 수는 복잡도의 대리값일 뿐)
- Todo·ScheduleBlock 전환 계획 전부, 7월 진행표·첫 커밋 흐름·"3단계 시작" 지시문
- 가짜 데이터로 전체 흐름부터 다시 만들기(지금은 실제 흐름 위에서 고친다)
- `is_fixed=false → DATE_MOVABLE` 일괄 변환(대상 열 없음)

### 10.3 보류 (다른 기능이 안정된 뒤)

- **diff 층**: 변경을 원래 자리에 겹쳐 보이기(떠나는 자리 흐리게, 오는 자리 점선). 판단 로직(`getDiffFor(executionItemId)` → UNCHANGED/OUTGOING/INCOMING/MODIFIED/CREATED/REMOVED)은 어느 뷰인지 몰라야 한다. 필요하다고 판단, 착수 시점 미정. 일정 주간 표에는 계획 초안을 겹쳐 그리는 코드가 이미 일부 있다.
- **flexibility**: 지금은 불필요(수업·알바는 `routines`·약속으로 분리돼 배치가 옮기지 않음, 마감은 `deadline_at`). 다시 꺼내면 5종 중 하나 고르기가 아니라 **독립 제약**(시각 고정·길이 조절·날짜 이동 범위·마감·횟수)으로, 아마 "고정" 잠금 하나부터.
- **Quick**: 전체 보류. 다시 꺼낼 때 순서 안: 기존 경로 묶기(오늘 조각 추가·방금 한 것 기록·AI 패널 열기) → 오늘 상태 3단계(수면·감정·컨디션) → 지출. Quick은 데이터를 소유하지 않고 기존 원본으로 보낸다. 상태·지출 저장 위치는 그때 정한다. 이력: 07-07 v2.1의 `quick_logs`(수면·감정 3단계), 08-03판의 네 진입점.
- 롤링 배치 미배치 이유 저장(지금은 응답에만 있어 새로고침하면 사라짐).

### 10.4 미결 (결정 필요)

- **시간 겹침 재검증**을 상담 변경 묶음·일반 AI 제안 적용에 붙일지, 막을지 경고만 할지(일부러 겹치게 두는 경우가 있음). 붙이면 계획 확정의 검사를 재사용한다.
- AI **해석**·반복 패턴을 기억으로 올릴 때 승인을 받을지(제안: 승인 필요).
- 우선 조각 추천 원칙(§5.5) 채택.
- 진행률 표시: v6.2는 게이지·이행률을 일괄 금지했다. "사용자를 평가하지 않는다"와 "필요한 진행 정보를 숨긴다"는 별개라는 의견이 있다.
- 부분 수행 남은 분량을 상담에서 다시 추정할지(§6).
